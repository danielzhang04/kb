# DRAFT — D1 fleet-ledger receipt design, 2026-09-08

**Status: renewed bounded correction applied; awaiting fresh independent review.** This remains a design-only draft and grants no implementation, merge, or publication authority.

This is a design note, not implementation authority. It replaces the earlier baseline-only proposal where it was unsound: a receipt phase must be durable before its next effect, and an ordinary shared daily cost shard has no per-settlement identity.

## Required reviewed ownership expansion

The D implementation would add a narrowly checkpointable transaction to `atomicJsonDocument.ts` and its tests. The transaction holds its existing SQLite `BEGIN IMMEDIATE` mutex, exposes the loaded document, and exposes `checkpoint()`. A checkpoint validates, fsyncs, and renames the current JSON snapshot before returning while retaining the mutex until the callback ends. The callback MUST let every checkpoint exception escape, including a falsey thrown value: it must not catch and return a normal value that would trigger the primitive's automatic final save. `begin`/`reconcile` catch that rejected transaction only after its lock has released and return `required`; they issue no later effect. The final callback return still performs the normal save then SQLite `COMMIT`; a `COMMIT` failure is likewise ambiguous. This is not a new generic business-store proxy: it is the existing atomic document's one lock-preserving durability primitive, needed because `mutate()` writes only after its callback returns.

It also adds an optional `day: str | None = None` argument to `scripts/ledger.py:append`, passed to `_shard`. Existing callers keep the default current-day behavior. Tests cover pinned-day, default compatibility, and a zero-byte pinned shard. The bridge's embedded script passes the day; it remains a call to `ledger.append`, never a second TSV writer.

The receipt shard format also requires a reviewed parser change in `dashboard/server/planeA/ledgers.ts` and tests in `dashboard/server/planeA/ledgers.test.ts`. `parseLedgerName` must recognize the reserved terminal suffix `--fleet-<64-lowercase-hex>` before the date anchor and return the original writer segment, not the whole decorated filename. `dashboard/server/agents/roster.ts` is the direct consumer of that parsed writer at `readLedgerWriters` (lines 295–304); no roster source change is needed if the parser normalizes it, but `dashboard/server/agents/roster.test.ts` must prove the decorated cost shard contributes rows/days to the original writer and creates no fake agent. `sliceLedgers` and `health/usage.ts` consume the same Plane-A writer slices transitively, so the Plane-A parser test must also prove the cost is attributed to the original writer. These are required scope additions, not incidental cleanup.

No `write/branch.ts` API expansion is needed. Its existing `publishPreparedCoordinationCommit` `validateCommit(commit)` hook already runs after the initial exact-path proof and, on every rebase, after the rebased exact-path proof and before the push decision. D supplies that hook as its proof-and-checkpoint callback: it proves the supplied commit's two owned paths and sidecar/postimage, records a replacement rebased SHA when necessary, and checkpoints it before returning to the publisher. A rejected callback prevents that push and leaves D at `required`.

## Receipt identity and shard format

`prepareFleetLedgerSettlement` remains pure: it validates and canonical-sorts `{ subject, runRef, rows: [{ cardId, model, costUsdMicros }] }`, rejects duplicate row identities, and hashes that immutable integer-micros snapshot for `receiptKey`. It does not read time or the filesystem.

`beginFleetLedgerSettlement` first runs the existing `assertFleetRunnable(repoRoot, runPreamble)` preamble, before a receipt lookup/intent, shard, sidecar, or Git action. A refused STOP/budget result creates no receipt and performs zero effects; because the fixed D port returns only `'settled' | 'required'`, it maps to `'required'` for B's retained reconciliation barrier. `reconcileFleetLedgerReceipt` repeats that gate before it touches an existing receipt; a later STOP/budget refusal returns `'required'` and cannot turn into a new append, commit, or publication. Only after a runnable preamble does `begin` capture one local `YYYY-MM-DD` day immediately before it writes the receipt intent. Instead of appending to the shared `<subject>-<day>.tsv`, it uses one normal cost shard per receipt:

```
ledgers/cost/<subject>--fleet-<receiptKey>-<day>.tsv
```

The optional Python `day` is a closed value: when supplied, `ledger.append` requires `isinstance(day, str)`, parses it with `datetime.date.fromisoformat`, and requires `parsed.isoformat() == day` before `_shard` forms any path. It rejects timestamps, short dates, traversal-like strings, and every noncanonical value. The TSV remains the established `billing`, `card_id`, `model`, `usd` cost record and is still created through `ledger.append`. `ledger.read_day` already globs every `*-<day>.tsv`, so `cost_today` and existing cost readers include it. The source subject remains the filename prefix and the receipt key is part of the shard identity, not an ignored extra column. The reserved 64-hex suffix is stripped only by `parseLedgerName`, so Plane A and the roster continue to attribute the rows to `subject`; a nonconforming suffix remains an ordinary writer name rather than being guessed.

Because that shard is receipt-unique, same-run repetition with byte-identical prepared input reuses the same key and file. The receipt document additionally indexes `(subject, runRef)` to its first immutable canonical input/key. A different canonical input for an already-recorded subject/run fails closed as `fleet-ledger-run-input-conflict`: D1 creates no second shard, appends no overlapping rows, and provides no amendment semantics. An explicit later amendment protocol would need its own reviewed identity and ledger meaning. A sidecar `ledgers/fleet-receipts/<receiptKey>.json` is committed with the shard. It contains the exact canonical input, receipt key, pinned day, shard path, and postimage hash. It is a governed `ledgers/**` artifact and gives Git recovery a unique witness when a commit lands before the local receipt checkpoint.

## Lock and phase algorithm

The local receipt document is `<stateRoot>/control/fleet-ledger-receipts.json`. Its existing SQLite mutex is an OS lock, so the checkpointed transaction serializes every D settlement/reconciliation process sharing that state root. The sole lock order is **`withOpsTransaction` outer, then receipt SQLite mutex**. After the zero-effect runnable preamble, every D begin/reconcile entrypoint enters the reentrant in-process ops transaction and then opens the receipt transaction for its complete effectful span. Existing create/publish helpers join that outer ops transaction. The publisher's `validateCommit` callback uses the already-held receipt transaction to update and checkpoint the record; it does not acquire another ops lock or receipt lock. Recovery uses the same order. No reverse receipt-first path is permitted. `withOpsTransaction` remains only an in-process `AsyncLocalStorage`/resource-limiter lock; it is not the cross-process receipt lock.

Inside the receipt mutex, the phases are:

1. Create or exact-match `intent` with the prepared snapshot and pinned unique shard, then call `checkpoint()` before any append.
2. Inspect the unique shard. It must be absent, header-only, or contain exactly a prefix of the sorted receipt rows with the expected header; malformed, reordered, extra, or non-prefix content returns `required`. Append only the missing suffix through pinned-day `ledger.append`. Re-read and require the complete exact row sequence and postimage hash. Write/re-read the exact sidecar, then set `rows-appended` and checkpoint.
3. Create one exact local commit containing only the unique cost shard and sidecar. Set `committed { commit }` and checkpoint before publication. If a crash occurs between those operations, recovery accepts only a matching `HEAD` whose two-path diff and sidecar/postimage are exact; otherwise it returns `required`, never guesses or creates another commit.
4. Call `publishPreparedCoordinationCommit` for that same stored commit and two fixed paths. Its existing `validateCommit` callback runs for the initial SHA and again after every rebase, before push. One shared D proof routine validates any supplied commit: it requires exactly one parent, requires the complete changed-path set to equal the receipt's cost shard and sidecar, reads those two blobs from that commit, requires the shard blob's hash to equal the durable postimage, and requires the sidecar bytes to equal the canonical bytes regenerated from the durable receipt's immutable key, prepared input, pinned day, owned paths, and postimage. The callback uses that routine and, for a replacement rebased SHA, replaces `committed.commit` with the supplied SHA and checkpoints before returning, so the publisher cannot push it first.

   Reconciliation has one bounded exception for a crash after Git rebases `HEAD` but before that callback/checkpoint. It applies only to a `committed` receipt when the stored SHA is not the current clean `HEAD`. While retaining the outer ops transaction and inner receipt mutex, D requires the checkout and index to be clean, reads only the current `HEAD` candidate, and runs the same exact one-parent/two-path/blob/sidecar/input/postimage proof above. If and only if it passes, D replaces `committed.commit` with that candidate SHA and calls `checkpoint()` before invoking the existing publisher. A checkpoint failure escapes the receipt callback and maps to `required` outside the lock; no publisher or later effect runs. This adoption does not inspect history, append rows, create or amend a commit, reset, rebase, publish, or mark completion. It never treats `HEAD` alone as evidence. A dirty checkout, absent/invalid candidate, extra or missing path, changed sidecar byte, wrong key/input/day/path/postimage, non-single-parent commit, or any proof failure returns `required` with zero append, commit, or publication.

   After the adoption checkpoint, normal publication resumes for that exact stored SHA. The existing publisher may rebase it again, and the same `validateCommit` proof/checkpoint rule applies before any push. After publication returns, the returned SHA must equal the currently checkpointed commit and is re-proven against exact bytes before `completed` is checkpointed. If it differs without that checkpoint, or cannot be proven/checkpointed, return `required`; never infer completion from working-tree `HEAD`. `PublishedCoordinationCommitError` records `publication-uncertain` with the last checkpointed SHA and returns `required`; reconciliation retries publication/proof only for that checkpointed commit, never append/create. Direct already-ancestor and outbox spool recovery use the existing publisher.

Any checkpoint, append, commit, or publication exception may have landed a preceding effect. It returns `required` and reconciliation uses only the stored prepared snapshot/key; it never reads new terminal rows or derives another identity.

## Cross-writer boundary

The receipt mutex proves exclusion among D callers sharing `stateRoot`. The unique cost shard means an unrelated legacy writer cannot create an indistinguishable matching row in that shard unless it deliberately targets the exact receipt-qualified subject. If it writes there anyway, a nonmatching row/postimage is drift and returns `required`; a byte-identical deliberate forgery is outside the ordinary writer interface and cannot be distinguished without a stronger repository-wide writer lock. D does not claim such a lock. B must replace the legacy settlement caller before D is composed, so normal production settlement has one writer per receipt shard.

## Focused evidence required before implementation acceptance

- pinned-day Python append/default and zero-byte compatibility, plus malformed/path-like/noncanonical day refusal;
- deterministic pure key/sort and duplicate refusal, plus same subject/run with a different snapshot refusing before any append/Git;
- held pre-intent checkpoint: zero append/Git;
- historical identical shared-day rows do not affect the receipt-qualified shard;
- crash after any prefix: reconcile appends only the suffix; malformed tail is `required`;
- identical repeated prepared input reuses one shard/receipt;
- crash after local commit before receipt checkpoint adopts only matching `HEAD` sidecar and makes zero duplicate append/commit;
- hold restart immediately after rebase changes clean `HEAD` and before `validateCommit`: the old-SHA `committed` receipt adopts only the exact one-parent candidate whose complete path set and two blobs prove the immutable sidecar/key/input/day/path and cost-shard postimage, checkpoints the replacement SHA before publication, and performs zero append/new commit; mutate either candidate blob, add a path, dirty the checkout, or fail the checkpoint and require `required` with zero append, commit, or publication;
- the existing `validateCommit` hook reuses that proof and checkpoints every later replacement rebased SHA before push; restart normally uses the checkpointed SHA, and no path searches history or automatically retries an uncheckpointed candidate;
- STOP/budget refusal before begin and before reconcile creates no receipt and runs no append/Git; an existing incomplete receipt remains `required` under that refusal;
- publication uncertainty retries only the same checkpointed commit;
- two receipt stores on one state root serialize their held operations through the SQLite mutex.
- decorated receipt filenames normalize to the original writer in Plane-A slices and the Agents roster, with no fragmented/fake roster identity.
