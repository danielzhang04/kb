## Executive decision

Keep KB's Git-native, human-readable governance and work-product trail. Stop making the dashboard's one serialized control document the durable execution engine. Retain a small control-plane API that owns identity, authorization, admission, human decisions, and immutable run/artifact references; move volatile execution state, queue delivery, leases, attempts, event logs, and terminal transcripts into a purpose-built durable store with retention. The initial candidate is SQLite WAL behind the sole dashboard/service writer (remote workers call that API; they do not share a database file). It is a hypothesis to test against a durable engine, not an irreversible commitment.

The near-term reduction is not “replace KB with n8n/Temporal.” It is to remove duplicated lifecycle reconciliation, whole-document hydration, Git-backed high-churn transport, and custom session/receipt plumbing while preserving the governance boundary that generic orchestration products do not supply.

### Cross-system conclusions

1. Durable systems separate **definition**, **control metadata**, and **volatile execution history**. n8n uses DB+Redis; Temporal uses persistence+task queues; Prefect has server state plus worker pools. ECC deliberately stays out of this category. KB should too: Git remains the reviewed definition/governance record, not a live queue or state database.
2. Treat **replay, retry and restart** as different API operations. Temporal validates that distinction. KB's UI should show: resume from a saved cursor/checkpoint, retry a selected attempt with a new immutable attempt ID, and restart a run from a stated stage. Do not call all three “replay.”
3. Human approval must be a durable **wait state** keyed by `runRef`, `stageRef` and `requestRef`, with a single idempotent response. LangGraph and Prefect support the pause side; KB uniquely needs authorization provenance and passkey/signed-deployment integration around it.
4. Retention is an engine feature, not cleanup folklore. LangGraph documents unbounded checkpoint growth; the existing KB store already has event/receipt bounds. Move that retention policy into the event/checkpoint store and expose it in health.

## Decision spike before choosing the engine

Implement the **same representative workflow** behind two thin adapters: (a) the proposed SQLite-WAL, sole-service-writer engine and (b) Temporal. The workflow must contain a durable human wait, an attempt that is killed after an acknowledged external side effect, a retry with an idempotency key, an operator restart from a stated stage, an artifact reference, and a deployed-adapter/version mismatch. Run the same injected crash/restart cases and verify the same run-detail/event DTOs.

Reject the SQLite/custom candidate if any recovery path needs a whole-document/global revalidation, cannot prove a single fenced/idempotent terminal effect after restart, requires two active authorities or cross-store atomicity, or exceeds the agreed slimness budget (new daemon/service dependencies, schema/migration surface, or bespoke recovery code). Reject Temporal if its deployment/worker/versioning and deterministic-workflow constraints add more operating surface than the demonstrated recovery guarantee requires. Record startup/recovery steps, fault results, code/dependency count and operator actions; choose based on that evidence. Postgres is a separate escalation only for measured multiple-writer/HA/database-separation needs.

## Two viable migration shapes

### A. Recommended: slim, owned run engine

Use SQLite WAL behind the sole dashboard/service writer as the initial runtime source of truth and keep the current dashboard/API. Add no Redis. The daemon owns scheduling and a small worker supervisor; workers pull a leased attempt through the API, emit append-only events, and persist a terminal result with compare-and-set/fencing. Git is read for approved work definitions and written through the current signed/outbox process for durable artifacts only.

This removes the giant aggregate hydrate path and lets KB retain its differentiated safety rules. It is the smallest path that still supplies persistent state, idempotency, leases, retry separation, human waits, runtime protocol checks and a shared API/UI DTO layer.

Migration sequence:

1. Freeze the existing public DTOs and add contract tests that serialize the same DTOs from old store and new read model.
2. Publish an immutable, post-commit event/snapshot feed from the existing store and replay it into a shadow repository; derive and compare read projections, but do not execute from it. Do not dual-write request paths or claim cross-store atomicity.
3. Select and record a pinned cutover generation/commit. Replay through that cutoff and validate the shadow projection; retain the old store as read-only fallback for historical runs.
4. Route **new** run creation, leasing/claims and human approvals to the new repository after the cutoff, making it the sole authority for those runs. Never allow two active authorities for the same run.
5. Export old runs as immutable audit bundles; keep a reader/migrator, not two active engines. Delete only after an explicit retention decision and restore drill.

### B. Borrow a durable engine

Use Temporal only for execution state/delivery: one KB run maps to a workflow, each tool/agent operation to an activity, and a human decision to a signal. Keep KB's policy gateway in front of any Temporal start/signal, and keep deployment/approval provenance in KB. This buys durable task queue semantics and replay but imposes deterministic workflow code and service operations.

This path is selected if it wins the decision spike. n8n is a weaker fit for this borrowing role because its node/credential/integration model is not KB's domain; LangGraph is appropriate only inside a worker that needs graph-level agent checkpoints, not as the global scheduler.

## Design constraints for the overhaul

- **One authority per datum.** Git owns reviewed policy/definitions; the run repository owns runtime truth; object storage owns bulky immutable bytes; the dashboard owns no independent mutable truth.
- **One schema source for UI/API.** Define versioned DTOs/contracts in a small shared module and validate at every HTTP/broker boundary. Keep Python deployment helpers generated from, or contract-tested against, that same schema rather than hand-maintaining parallel state models.
- **Authorization before enqueue, capability-limited at execution.** The policy gateway resolves an approved runtime/profile/tool allowlist into the attempt. The worker receives only that resolved capability set, not a raw card or arbitrary MCP configuration.
- **No global acceptance invariant on the hot path.** Validate the target run and its referenced rows in a transaction. A periodic integrity scanner may quarantine bad records and alert, but must not turn one historical record into an outage for unrelated runs.
- **Retention and audit are explicit.** Immutable events/artifact manifests are retained by class; operational logs/checkpoints have TTL; audit export is read-only and checksum-addressed.
