# Supporting platform audit (DRAFT)

Date: 2026-09-06
Scope: supporting platform subsystems named in the audit commission. This is a static/code-and-focused-test audit, not a production observation. It does not establish which model responded at runtime.

## Executive result

The component libraries are generally defensive: workflow compilation validates declaration/profile/runtime bindings; learning proposal generation is bounded to five drafts and cannot publish directly; reconciliation funnels mutations through one publisher; eval evidence is reserved away from autonomy promotion; and placement contracts are exact-key decoded. The main problem is not an absence of well-tested components but missing or incomplete composition between them.

1. **HIGH — the production daemon cannot expose the node placement protocol.** `BuildAppOptions` has no node identity or v1-port fields (`dashboard/server/index.ts:145-179`), and `buildApp()` passes none to `makeSurfaceContext()` (`index.ts:220-235`). `registerV1NodeRoutes()` fails closed when those fields are absent (`dashboard/server/api/v1/routes.ts:195-200`). The source itself says Desktop advertisement transport is “not built here” (`index.ts:241-247`). Thus claim, renew, report, and remote host advertisement exist as unit-tested services/routes but have no production binding; full-surface daemons instead advertise into independent local documents. Trigger: start through exported `start()`/`buildApp()`. Outcome: no node routes/federated placement, so cross-host execution cannot work through the designed protocol. Confidence: high.

2. **HIGH — seven System learning schedules have no FIRE-to-runner integration.** `execution.ts` explicitly labels `resolveExecutionPath`, all three `run*` functions, and `implementerBatchRegistry.record()` as library/test-only and says live integration has not landed (`dashboard/server/learnings/execution.ts:18-30`). Repository tracing found no production caller of those functions. A separate trace through `control/queueBridge.ts` found neither the seven schedule IDs nor these semantic resolver/runner symbols; it is therefore not an alternate executor for these System paths. `index.ts` constructs the registry and starts merge polling (`index.ts:368-412`), but never records a batch, so the Implementer retirement input remains empty. Trigger: a seeded System schedule fires. Outcome: the dashboard does not dispatch the declared Producer/Implementer/Sweeper path; an Implementer PR also cannot enter the live retirement loop through this composition. Confidence: high.

3. **HIGH integration blocker (latent, not a current live exploit) — lease renewal and reports accept the complete absence of a fresh capability advertisement.** The port contract defines `undefined` as “no fresh advertisement” (`dashboard/server/placement/leaseService.ts:33-34`), while renewal promises `capability-lost` when live capability is lost (`leaseService.ts:98-101`). The implementation rejects only a *defined, different* hash (`leaseService.ts:108-110`); report admission repeats the condition (`dashboard/server/placement/reportService.ts:110-113`). A read-only inline reproduction returned `{ok:true}` for renewal with `currentAdvertisedCapabilityHash() => undefined`. Trigger after production binding: advertisement expires/disappears while the lease itself remains unexpired. Outcome after production binding: the worker could renew and submit progress against capability proof that is no longer fresh. Finding 1 currently masks this path because the production daemon does not bind the node routes. Guards present: wrong host, expired lease, revision and sequence checks; missing guard: `undefined => capability-lost`. Tests cover matching/mismatching hashes but not the missing-advertisement case. Confidence: high in the service contract defect and reproduction, with no claim that the unwired route is currently exploitable.

4. **MEDIUM — semantic Brain results have no source-revision freshness contract.** The indexed corpus is explicitly selected (`scripts/brain/indexer.py:17,31-37`) and the manifest records model, dimensions, count, time, roots, and chunker (`scripts/brain/store.py:93-104`), but no commit, corpus digest, or per-file revision. Search returns the loaded index as a normal success (`dashboard/server/brain/routes.ts:70-82`), and repository tracing found no rebuild watcher/cadence. Trigger: a corpus file changes after the last manual build. Outcome: callers receive stale memory/STATE/handoff snippets without a machine-readable stale flag. Model fingerprinting protects embedding compatibility, not content freshness. Confidence: high.

5. **MEDIUM — learning/maintenance inputs are bounded but not all trust-attributed.** `agent_maintainer.py` is correctly draft-only and caps output at five (`scripts/agent_maintainer.py:3-6,32,772-819`), but `_grade_proposals` consumes failing ledger rows without applying `promotion.allowed_graders()` or git-author attribution (`agent_maintainer.py:422-447`), and `_memory_proposals` treats any matching failure phrase in an agent memory shard as evidence (`agent_maintainer.py:449-459`). A planted or malformed source cannot self-apply a change because the target wall and human-review draft boundary hold; it can, however, create noisy or misleading proposals. Treat these sources as untrusted suggestions or attach provenance/trust status in the draft. Confidence: high.

6. **MEDIUM — open Implementer PR tracking is process-local and not reconstructed.** The registry intentionally uses an in-memory `Map` and documents that after restart a forgotten batch “is not re-polled until re-opened” (`dashboard/server/learnings/execution.ts:350-377`). The retire action is replay-safe, but that prevents duplicate retirement; it does not rediscover an already-open/merged PR. When FIRE wiring is added, a restart between publication and retirement can strand learning records unless boot reconstructs the batch from durable receipt/PR metadata. Confidence: high as a design/restart gap; currently masked by finding 2.

## Coupling and completeness measurements

- Family implementation footprint: workflows 7 files/4,274 lines; reconciliation 6/2,089; placement 12/1,386; runtime 7/1,255; learnings 4/1,074; composer 3/506; release 3/170; brain 1/100; registry 2 files. `dashboard/server/context/` does not exist; HTTP context lives in `dashboard/server/http/context.ts`.
- The v1 placement API has three layers (route, service port, store operations) but production composition supplies zero of its node identity/port dependencies. This is high structural coupling without a completed ownership seam.
- Learning execution centralizes seven schedules, three runners, PR publication, an in-memory registry, merge polling and composition in one 500+ line module. Split declaration/path resolution from effectful runners and durable batch discovery.
- `reportService.ts:134-146` expresses one logical report transition as 2-3 separately awaited writes. No production ReportStorePort exists yet, so this is not reported as a reproduced active corruption bug; the eventual adapter must implement the transition atomically or with a durable idempotent receipt before production binding.

## Staged verification required by the overhaul

1. **Composition/parity:** factory-generated declaration -> roster -> workflow default -> compiler -> placement requirement; fail on unknown profile/model/runtime and schema/parser divergence. Exercise role, skills, memory and Brain/search surfaces in the same parity fixture.
2. **Placement fault isolation:** production-like VM/Desktop composition must enumerate node routes, advertise one shared VM-side table, claim a run, renew, report, and proxy reads. Remove/stale the advertisement before renew/report and require `409 capability-lost`.
3. **Atomic/idempotent report:** inject a failure after event append, after sequence bump, and before gate/terminal write; retry the same sequence must converge to exactly one event and the intended gate/terminal state.
4. **Restart:** publish an Implementer batch, restart before merge and after merge, reconstruct from durable metadata, poll, and retire exactly once. Also rebuild Brain into a new generation while queries continue; readers see either old-complete or new-complete, never mixed files.
5. **Concurrency/bounds:** race two claims and two report submissions; assert one lease winner and monotonic sequence. Fire overlapping learning schedules; enforce one bounded batch per operation key, maximum five candidates, no self-approval, and an independent/trusted judge.
6. **Freshness:** mutate a corpus file after indexing and require the API to return `stale` (or refuse) until a generation with the matching source digest is activated.

## Recommendation summary

- **Keep:** strict workflow compiler, bounded draft-only maintainer, reserved eval evidence, target walls, single reconciliation publisher, exact-key placement contracts, offline model fingerprint validation.
- **Remove/avoid:** process-only ownership of durable PR lifecycle; comments that describe future production bindings as though they exist; silent success when capability evidence is absent.
- **Redesign first:** a production composition root for node placement and System FIRE routing; durable/idempotent learning batch registry; atomic report transaction; versioned Brain generations with source freshness and trusted-memory provenance.
