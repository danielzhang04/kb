# Figment architecture: code evidence at `a005f6d0`

Scope: local, read-only architecture audit of the implemented Figment front half, its declared S2-S9 workflow, and ignored run receipts. No model judge, network, pod, credential, or media inspection was performed. The required preamble failed because the daily budget was already exceeded; the operator explicitly authorized this documentation audit to continue. Confidence is high for repository structure and reachable code paths. Current provider state is unknown because only local receipts were inspected.

## Executive finding

Figment is currently a capable **persona-conditioned image dataset and LoRA experiment harness**, not an end-to-end 10sorlabs-like creator studio. The executable spine is `figment_train.py`: plan immutable-ish manifests, launch the shared RunPod harness, verify receipts, build identity/judge boards, apply operator rulings, train, test checkpoints, and generate stills. It includes inline generation and re-detailing, while most of the broader S4-S9 architecture (register proof, production pass lifecycle, video, weekly planner, publish, insights, voice, and multi-account operation) exists as workflow and agent declarations without the named runners. The workflow itself is not dashboard-valid because it names an unregistered execution profile.

## Top architectural gaps

### 1. HIGH — “gate” is two incompatible contracts, and the live driver does not consume the SHA-bound human gate

`gates.py` calls itself the sole `gate.json` writer and defines a human decision bound to `subject_sha256` (`gates.py:1-11,56-113`). Separately, `build_grade` writes `grade/<stage>/gate.json` directly using the unrelated `figment/gate@1` per-cell score schema (`figment_train.py:2097-2107`; `identity_gate.py:394-407`). `apply_rulings` trusts that second file by image id and permits a human `gate_override` for failed cells (`figment_train.py:2218-2257`); it never calls `gate_is_current` or verifies image/persona/config hashes. A changed image, threshold file, or persona can therefore retain an apparently usable old grade document. The README also says rerunning `gate` after a threshold edit shows the new result (`README.md:168-170`), but `command_gate` explicitly only rereads the old file and never recomputes (`figment_train.py:2356-2371`).

Concrete outcome: the architecture cannot currently prove that an approval applies to the bytes and policy being trained or promoted. The intended stale-gate protection exists, but on a disconnected artifact type.

### 2. HIGH — train-first bypasses the claimed human-curation boundary

The live path is documented as an “already-graded, already-captioned” dataset (`README.md:44-52`). `build_train_first_plan`, however, requires only two filenames, `_dataset.ready` and `dataset_manifest.json`, then copies directory contents and writes a new marker (`figment_train.py:1449-1517`). It does not validate the manifest schema, declared hashes/count, captions, source selection, operator rulings, safety axes, or a SHA-bound approval. Its upstream selector filters `same_person`, `age_delta`, and `artifacts` numerically (`select_training_cells.py:217-247`) and, when reading `figment/gate@1`, ignores the row's overall `pass` and operator rulings (`select_training_cells.py:181-209`). Anchors are always admitted unscored (`select_training_cells.py:108-122`).

Concrete outcome: any directory with those marker names can enter a paid LoRA run, including cells that failed the combined gate or were never operator-reviewed. The tracked 23-image selection is auditable, but the CLI does not enforce that lineage.

### 3. HIGH — the declared S2-S9 dashboard workflow is not launchable

The definition declares `profile: creator` (`workflows/figment-creator.md:1-10`). Dashboard parsing refuses any profile absent from the server-owned set (`dashboard/server/workflows/defs.ts:1188-1194`), whose tests pin the complete set to `checker-readonly,research,gmail-triage,drive-author,producer,scanner` (`dashboard/server/workflows/profiles.test.ts:5-7`). The local Figment workflow suite passes 22 tests, but it parses YAML itself and only checks custom structural rules (`workflows/tests/test_figment_creator_workflow.py:57-68,205-263`); it does not exercise dashboard registration or compilation.

Concrete outcome: the studio-shaped DAG can be read as documentation but cannot be launched from the dashboard at this commit.

### 4. HIGH — tester rulings cannot promote a checkpoint into generation

Generation refuses to build its manifest unless `training.yaml` already contains a positive `chosen_checkpoint_step`; its error tells the operator to run `apply-rulings --stage tester` first (`pipeline/figment_train.py:970-980`). The config loader accepts that field when supplied (`pipeline/training_config.py:18-22,151-157`), but `apply_rulings` has materialization branches only for `dataset` and `anchor`. Its tester path falls through to generic approved-list output and never updates `training.yaml`, the persona, or the run plan (`pipeline/figment_train.py:2181-2353`). A repository-wide reference check found no other writer for `chosen_checkpoint_step`.

Concrete outcome: the documented command cannot make generation planable. An operator must hand-edit the sidecar, and the integer is not tied to an approved tester candidate or checked against the produced checkpoint ladder. **Confidence: high.**

### 5. HIGH — most of the 10sorlabs-like value chain is declarations without runners

The mandate requires register lock, pass-based stills, video, research-driven planning, publish/measure, optimise, voice, and a multi-account studio (`MANDATE.md:15-56,114-131`). The actual pipeline directories are `bakeoff`, `calibrate`, `calibration-study`, `content`, `expand`, `pod`, `tests`, `train`, and `workflows`; `register`, `passes`, `video`, `voice`, `publish`, and `insights` are absent. Content has three data YAMLs and a data test, not the workflow's named `plan_week.py`. The workflow's artifact paths and agent prose are therefore specifications, not executable integration.

Concrete outcome: still-generation and re-detail code exists, but no code path promotes an operator-accepted checkpoint into register proof and then carries that approved identity through the declared production Pass A/B, video, calendar, publication, measurement, and feedback lifecycle.

### 6. MEDIUM — lifecycle and resume claims are narrower than the docs imply

`run --stage all` stops for operator action only after `dataset` (`figment_train.py:1819-1827`). If a no-history persona's plan includes `anchor`, the loop marks anchor complete and proceeds directly into dataset generation (`figment_train.py:1286-1297,1735-1758`), so the anchor eye-gate described by the mandate does not block that chain. Resume skips completed runs/stages, but a `running` receipt requires manual investigation and a `failed` receipt permanently refuses relaunch from the same reviewed plan (`figment_train.py:1762-1777`); there is no checkpoint-resume or reconciled retry transition. The stage-skipping predicate also treats mere existence of `grade/<stage>/rulings.json` as settled without digest validation (`figment_train.py:1748-1758`).

Concrete outcome: “all resumes” is true only for the dataset stop and already-complete runs. It is not a general crash/failure recovery mechanism, and it does not enforce every advertised human stop.

## Other material findings

- **MEDIUM, high confidence — persona model metadata is split-brain.** `creator-001/persona.yaml` declares `lora.base: flux2-klein-base-4b` (`persona.yaml:91-96`), while `training.yaml` declares `base_arch: krea2` (`training.yaml:2-13`). `persona.py` only checks that `lora.base` is a nonempty string (`persona.py:433-435`); execution derives the trigger and manifests from the training sidecar (`training_config.py:172-181`; `figment_train.py:330-355`). The stale `lora.base` does not alter current training, but any dashboard or future downstream stage reading the base persona gets the wrong model lineage.
- **MEDIUM, high confidence — clean-checkout reproducibility is incomplete.** Persona loading requires referenced anchors to exist (`persona.py:309-323`), while all persona anchor directories are ignored (`.gitignore:49`). A focused creator-002 acceptance run on the clean snapshot failed first because those referenced anchors were absent. After the three ignored fixture anchors were supplied locally, persona validation still failed because the declared `identity.spec.sha256` did not match the checked-out spec bytes after the repository's Windows line-ending conversion. The repository therefore cannot reproduce persona acceptance or plans from commit `a005f6d0` alone. The source/config hashes and manifest verification are useful controls once portable assets and digests are present (`figment_train.py:1393-1409,1779-1787`).
- **MEDIUM operational receipt, current provider state unknown — two latest local tester receipts recorded unverified teardown.** `c001-tf3/.../run.json:27-40` and `c001-tf4/.../run.json:27-40` each record `termination_verified:false` and `PodStillRunning`. This shows the harness correctly fails loudly rather than claiming success, but local evidence does not establish later cleanup. No provider query was made. Earlier anchor/training/tester receipts do show verified termination, including the five-checkpoint train at `c001-tf/.../run.json:358-412`.
- **LOW, high confidence — persona generality is creator-general but architecture-specific.** Creator ids, references, look clauses, trigger and output names are data-driven (`figment_train.py:330-470`), and Krea-2 is intentionally the only accepted training architecture (`training_config.py:24-31,114-117`). “creator-002 differs only by data” is reasonable only when external anchors/spec hashes are supplied and Krea-2 remains the architecture.
