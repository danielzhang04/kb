# Dashboard v3 P6 implementation plan

## 1. Goal + success condition

Implement only design section 10 P6 (`docs/specs/2026-08-20-dashboard-v3-design.md:623-637`). Every service that a current `/api/*` handler owns inline is extracted into one shared function; `/api/v1` is registered as a second URL over those same functions with frozen per-kind ETags, watermarks, and cursors; the control store gains `HostAdvertisement` and `PlacementLease` records behind one migration; the scheduler picks a host by capability matching instead of a platform constant; a root-owned `/etc/kb-dashboard/host-nodes.json` map plus a trusted-proxy-injected `Tailscale-Node-ID` becomes the sole daemon identity; and the Desktop daemon claims leased work and reports `started|event|gate-opened|completed|failed` back to the VM with a node-derived host, lease revision, and monotonic sequence.

P6 is complete only when every Verify item at design line 633 has non-skipping evidence: the three Windows dashboard commands and the four WSL-clone commands exit zero; the named Python suites exit zero; the two-daemon integration fixture — two daemon processes on one machine over loopback with a fixture node map, synthetic Gmail/browser connectors advertised only by the Desktop daemon and a VM-only agent — runs green with no `.skip`; contract tests cover **every** §7 endpoint's exact ETag/watermark/create precondition, stale cursor, idempotency conflict, T3 WebAuthn refusal, node enrollment/rotation/revocation, and object authorization for advertise/claim/renew/report; and an old-route launch and a `POST /api/v1/runs` launch of the same owner produce byte-identical `Run.owner`, `Run.executionHost`, and terminal-outcome records. The browser proof is that a VM-scheduled Desktop run shows as one run, one stream, and one gate on both dashboards, and that lease expiry and reclaim leave exactly one owner. Every adversarial probe of design 635 and §9 (`design:529`) passes, and Daniel enrols the Desktop node, runs a Desktop-only agent from the VM, and watches it from both hosts.

Execution is W0, then width-five W1-W5, then serial W6.1-W6.5: **11 tasks**. W0 freezes the cross-language contracts. Parallel tasks own disjoint files and read only W0 contracts. Route registration, existing callers, UI, deletions, spec text, and proof harnesses change only in serial verticals. Each task starts with its named failing test, ends at its literal checkpoint, and never commits.

## 3. Domain/contract deltas

`[SPEC]` is fixed by the cited design spec. `[PLAN]` closes a choice the spec leaves open. W0 makes every type and vector below compile before any behavior work.

### 3.1 `HostAdvertisement` and `PlacementLease`

`[SPEC]` Both interfaces are design 388-408 **verbatim**; W0 copies them character for character into `dashboard/server/placement/contracts.ts`, and a test asserts the field list against a frozen fixture so a silent rename is a failure.

`[PLAN]` Field domains, all enforced by exact-key decoders in the `p2Decoders.ts:29` style:

- `hostId` reuses the existing `HostKind` (`p2Contracts.ts:12`). There is no third host and no host string anywhere else.
- `daemonVersion` matches `/^[a-z0-9][a-z0-9.\-]{0,63}$/`; on the VM it is the immutable release `sourceCommit`, on Desktop the daemon's package version. It is display and diagnostics only, never an authorization input.
- `reportedAt` is RFC 3339 UTC. An advertisement is **fresh** for 90 s; a stale one is never a placement candidate (`design:635` "stale advertisement"). Freshness is computed against the VM store's clock, never the reporter's. **Every daemon re-advertises on a 30-s timer against that 90-s window, so three consecutive misses are tolerated before a host stops being a candidate** — an interval at or above the window would make every launch `no-complete-placement` [P6-C44]. The interval and the window are one shared constant pair in `placement/contracts.ts`, not two literals.
- `connectors`, `skills`, `filesystemRoots` are sorted, unique, and already canonical (§3.2). `filesystemRoots` entries are symbolic ids matching `/^[a-z0-9][a-z0-9\-]{0,63}$/`; any `/`, `\`, `:`, `.`, or `..` is rejected at decode, so an absolute client path cannot enter the record (`design:394`). Bounds: ≤ 64 connector servers, ≤ 128 tools each, ≤ 256 skills, ≤ 64 roots; over-bound input is `413`, not truncation.
- `pty` is the `RuntimeCapabilities` discriminant (`capabilities.ts:28`), not an OS guess. `gpu` is a probed boolean that defaults **false** when the probe fails.
- `clis` is exactly `{claude, codex}`, each `ready | missing | login-required`. Only `ready` satisfies a requirement; `login-required` is a visible non-match, never a retry.
- The record carries a plan-owned `version: number` beside the spec fields — design 428's "independent numeric version" — incremented on every accepted `PUT`. It is the advertisement ETag domain and is unrelated to the lease revision.

`[PLAN]` `PlacementLease` domains: `runRef` is the existing run key and is the **primary key**, so at most one lease row per run exists by construction — this is what makes split brain impossible rather than merely unlikely. `capabilityHash` is `sha256` over the canonical JSON of the sorted normalised requirement (§3.2), 64 lowercase hex, always recomputed server-side and never accepted from a caller. `revision` starts at 1 and increments on every accepted claim, renew, or report. `expiresAt` is 120 s from claim or renew; a renew after expiry is refused rather than resurrecting the lease. `lastReportSequence` starts at 0.

`[PLAN]` **Three** collections — `hostAdvertisements`, `placementLeases`, and `v1Idempotency` [P6-C37] — join `StoreDocumentCollections` (`store.ts:461-480`), `CONTROL_PLANE_COLLECTIONS` (`controlPlaneSchema.ts:3`), and the compile-time equality at `store.ts:489-494`, and commit at durability `'ordinary'` — a placement is not a release transition.

### 3.2 Capability requirement, canonical normalisation, and matching

`[SPEC]` Design 383: placement requirements are the union of workflow-level capabilities and every assigned stage agent's capabilities. Design 410: the scheduler expands declared tools/connectors/skills/root ids and selects a **fresh** host whose advertisement contains every requirement; VM wins a tie; Desktop wins whenever it is the only complete match; **no partial placement occurs**.

`[PLAN]` `CapabilityRequirement = {connectors: Array<{server: string; tools: string[]}>; skills: string[]; filesystemRoots: string[]; pty: boolean; gpu: boolean; clis: Array<'claude'|'codex'>}` — the exact subset of `HostAdvertisement` that can be required. `daemonVersion`, `reportedAt`, and `hostId` are deliberately **not** requirable: a requirement that could name a host would reintroduce the tier routing P6 deletes.

`[PLAN]` **Normalisation happens exactly once** (`design:637`), in `placement/normalize.ts`, at declaration read: NFC, trim, lowercase ASCII, `_` → `-`, collapse repeated `-`, then reject anything not matching the id charset. The stored requirement and the stored advertisement are both already canonical, so `match()` refuses a non-canonical input with `invalid-capability-name` instead of normalising again. A property test asserts idempotence over the full accepted charset and over every rejected class.

`[PLAN]` `match(requirement, advertisement)` is true iff: every required connector server appears in the advertisement with a **superset** of the required tools; `skills` and `filesystemRoots` are subsets; `pty` and `gpu` are implied (`required → advertised`); and every required CLI is `ready`. Selection over the fresh advertisements is: zero complete matches ⇒ the launch refuses `409 no-complete-placement` and **no Run row is created**; one ⇒ that host; both ⇒ VM. The refusal is terminal for that request — P6 adds no queued-until-capable state, because a queued run would be a partial placement in slow motion.

`[PLAN]` **The never-run entity chip has a defined source once the tier preview is deleted** [P6-C39]. ux-rule 3 requires a VM/Desktop chip always, and an entity that has never run has no `Run.executionHost` to read. When at least one advertisement is fresh, the chip shows the projected placement. When **no** advertisement is fresh, it falls back to the serving daemon's own composed capability host — `runtimeExecutionHost` (`runtime/capabilities.ts:106-110`), which P6 keeps precisely for this — and is labelled as the daemon's self-identity, never as a placement claim. The client still computes nothing: the fallback is resolved server-side and shipped as the same field.

`[PLAN]` `capabilityHash` is bound into the lease at claim. A **capability loss** (the host re-advertises without a required capability) leaves the lease intact but makes the run undispatchable: the next renew is refused `409 capability-lost`, the lease is released, and the run is re-placed once. It is never silently downgraded onto a partial host. This is design 635's own clause and it carries **its own manifest id, `capability-loss` (21)**, no longer folded into `false-capability` [P6-C50].

### 3.3 Node identity, the root-owned map, and enrollment/rotation/revocation

`[SPEC]` Design 414: operator browser auth and daemon auth are separate; `OPERATOR_SUBJECT` plus `tailscale-user-login` from `auth/mode.ts` **cannot** call advertisement/lease/report routes. Bootstrap extends the trusted loopback proxy to strip inbound identity headers, resolve the remote peer through Tailscale LocalAPI `WhoIs`, and inject canonical `Tailscale-Node-ID`; the app accepts that header only after the existing proxy-uid/full-4-tuple proof. Design 416 fixes the map file, its `0444` root ownership, the schema literal, boot validation, rotation semantics, and that authorization derives host id from the map, **never** from the path or body.

`[PLAN] [P6-C19] Spec-versus-tree conflict and its narrowed resolution.** There is no extensible loopback proxy in the tree: the trusted proxy is `tailscale serve` running as root, which injects `Tailscale-User-*` and cannot be taught `WhoIs` injection (`auth/tailnetOperator.ts:23-24`, `deploy/bootstrap_vm.py:236`). "Extends the trusted loopback proxy" is implemented by **inserting** one — but the insertion is narrowed on every axis the r1 review found unsound.

**Topology (restated, because it is the whole safety argument, and r2 blocker 1 falsified the previous statement of it).** The split is **by peer uid behind two `tailscale serve` listeners, never by path prefix** [P6-C46]. - **Operators:** `tailscale serve` on **443** (root) → dashboard loopback. A dead proxy degrades placement; it never takes the dashboard down. **This is a plan ruling inside the design's own words, not a specification edit.**

`[PLAN]` The map loader (`auth/hostNodeMap.ts`) reads `/etc/kb-dashboard/host-nodes.json` once at boot and validates: the exact schema literal `kb.host-node-map/v1`; `revision` a positive integer; exactly the keys `{schema, revision, hosts, revoked}` and `hosts` exactly `{vm, desktop}`; each `nodeId` matching `/^[A-Za-z0-9]{5,32}$/`; the two active ids distinct **and** absent from `revoked`; `revoked` entries unique with RFC 3339 `revokedAt`. On Linux it additionally stats the file and refuses a non-uid-0 owner or any group/other write bit. **Every failure fails closed the same way**: the node-authenticated routes answer `503 host-map-unavailable`, Health shows one integrity row, and the operator surface is untouched — a bad map must never take the dashboard down, and must never let a node in.

`[PLAN]` Enrollment and rotation are file edits Daniel makes through bootstrap/deploy review; there is no enrollment endpoint and no hot reload. Rotation adds the old id to `revoked`, increments `revision`, and restarts both sides; **boot then releases every `PlacementLease` whose host maps to a revoked id**, emitting exactly one durable event per released lease, and the affected runs are re-placed once or contained as `waiting-human`. Replaying the same boot is idempotent.

`[PLAN]` Attribution and separation are two hooks, never one: `requireNodeIdentity` resolves `Tailscale-Node-ID` → map → `HostKind` **after** the existing peer-uid proof, and refuses `401 untrusted-peer`, `403 node-unknown`, `403 node-revoked`, or `503 host-map-unavailable`. `requireOperator` is unchanged. An operator subject on a node route is `403 operator-not-a-node`; a node identity on any operator route is `403 node-not-an-operator`; a node identity on the human-response route is `403 host-response-forbidden`. Those three are **subject** refusals; the two **peer-uid** refusals of [P6-C46] are evaluated first and independently — a node route reached from any peer other than `DASHBOARD_NODE_PROXY_UID` is `403 node-route-only`, and any operator route reached from that uid is `403 operator-route-only`, whatever subject the request carries. `:hostId` in a URL is validated **against** the map-derived host and is never the source of it.

`[PLAN]` **Node routes are metered on their own budget** [P6-C33]. Today one guard pair serves every governed route (`index.ts:231`, `http/surface.ts:435`, mutation budget 30/min with a 5-minute lockout), so a Desktop daemon renewing a 120-s lease and reporting per event would trip Daniel's own write budget, and a looping or hostile node would lock him out of the write surface entirely. The node scope therefore constructs a **separate `nodeRateGuard` instance**, keyed per node identity, and sized **above** the real traffic rather than at it [P6-C52], because r2 showed the previous numbers throttled the very clients they were written for: **claim 4 per 60 s** — a 204-on-timeout client that re-claims immediately after a 25-s long-poll must never `429`, and at 1 per 25 s it did so on jitter; **renew 6 per 120 s** — a 120-s lease needs four renewals plus room for two retries, which 1 per 30 s did not leave; **report 60 burst then 10/s** sustained. Exceeding it is `429` for that node only. §9's `node-flood` probe drives traffic **above** these budgets and proves the operator write surface stays responsive while a node is being throttled.

### 3.4 The v1 envelope, per-kind revision domains, cursors, and preconditions

`[SPEC]` Design 420 verbatim: success is `{apiVersion:"v1",kind,data,meta:{etag?,watermark?,nextCursor?},actions?}` with fields not meaningful to that kind **absent**; errors are `{apiVersion:"v1",error:{code,message,retryable},meta:{currentEtag?,currentWatermark?}}`; there is no universal `revision` domain. Design 422-429's six-row table is the authoritative ETag/watermark contract and W0 encodes it as six fixtures. Design 431: missing precondition `428`, mismatch `412` with the current ETag/watermark, key reuse with a changed body `409`; a cursor encodes kind, watermark, filter hash, and last stable sort key, and is `409 cursor-stale` once its watermark moves. Design 433 fixes the body naming shared by old-route adapters and v1 clients: `expectedOwnerEtag`, `expectedRequestRevision`, `expectedCollectionWatermark`, and schedule create's numeric `expectedCollectionRevision`.

`[PLAN]` The six domains are **branded types with no mutual assignability** — `ItemEtag`, `RunEtag`, `ScheduleItemEtag`, `ScheduleCollectionWatermark`, `SourceRevisionWatermark`, `HostVersion`/`LeaseRevision`, `AggregateWatermark`. There is no generic `compareRevision`, no shared `revision` field on the envelope, and W0 ships compile-negative vectors proving a Run ETag cannot be passed where a schedule watermark is expected (`design:637`). String forms: `run:<runRef>:<version>`, `schedule:<id>:<version>`, `schedules:<scheduleCollectionRevision>`, `host:<hostId>:<version>`, `lease:<runRef>:<revision>`; item ETags for agents/workflows are their source hash unchanged. `[PLAN]` **Preconditions follow design 431 exactly, and `428` and `412` are different failures** [P6-C45]: an **absent** precondition on a mutating route is `428 precondition-required`; a **present but stale** one is `412` carrying the current ETag or watermark. The Health watermark, which can never be a precondition at all, is therefore `428 precondition-required` when a mutation presents nothing and `412 watermark-not-a-precondition` when it presents the watermark as `If-Match` — both are refusals, and neither is a `400`.

`[PLAN]` `Idempotency-Key` matches `/^[A-Za-z0-9_.:-]{16,128}$/`. **Records live in one new store collection, `v1Idempotency`, added by the same v4 migration** [P6-C37] — not a second store, not a new subsystem, and not the namespaced launch key at `control/launch.ts:170-172`, which keeps doing its own narrower job. Each row keys on `(actorOrNodeId, method, URI, key)` and stores `sha256(canonical body)` plus the original status and body bytes; an identical replay returns them verbatim, a changed body is `409 idempotency-conflict`, and rows expire after 24 h, swept by the same 60-s sweeper that reclaims expired leases (§3.5). **Ownership splits at the decoder** [P6-C59]: **W0** owns the record decoder in `api/v1/idempotency.ts` — the key grammar, the canonical-body hash, and the exact-key wall over the stored row — and **W1** owns the collection, the v4 migration that adds it, and the TTL sweep, importing W0's decoder and writing none of its own.

`[PLAN]` **The rule, stated once** [P6-C69, P6-C80 ruling 2]: **keyed** = every mutation whose replay is not already made idempotent by a CAS precondition (claim, human-response, operator mutations); **exempt** = advertisement, reports, renew — and nothing about the three writes a `v1Idempotency` row. Design 431 reads "All mutations require the authenticated actor, `Idempotency-Key`, and the kind-specific precondition above. Missing precondition is `428`; mismatch is `412` with current ETag/watermark; reuse of a key with a changed body is `409`" — a key is what stops a **replay from duplicating an effect**, and all three exempt routes already have a stronger stop of their own. `PUT /api/v1/hosts/:hostId` is CAS'd on `host:<hostId>:<version>`, so a replayed advertisement is a **no-op by CAS**, not by key; `POST /api/v1/runs/:runRef/leases/renew` is CAS'd on `expectedLeaseRevision` on the identical rationale, so a replayed renew is also a **no-op by CAS**; `POST /api/v1/runs/:runRef/reports` is pinned to `sequence === lastReportSequence + 1`, so a replayed report is `409 report-out-of-order` with no state change. Requiring a key on any of the three would instead write one row per beat — at §3.1's 30-s interval, ~2 880 rows per host per day plus one per run event plus one per renew — into the single control document `store.ts:3029-3032` rewrites on every commit, which is a durability cost bought for nothing. The exemption is stated in §6's implied sentence and asserted by §9's `changed-idempotency-replay` probe.

`[PLAN]` Cursors are opaque base64url over `{kind, watermark, filterHash, lastKey}`, HMAC'd with a **persisted per-store cursor secret** [P6-C41] — generated once, stored in the control document, and therefore **surviving daemon restart** and **identical on both daemons**, so a VM-minted cursor verifies at the Desktop daemon and `one-stream-both-hosts` works across a restart. A cursor whose watermark has moved is `409 cursor-stale`; **rotating the secret is also `409 cursor-stale`, never a `400`**, because the client's correct response is to restart the stream. Only a hand-edited or truncated cursor — one that fails the HMAC under the current secret and is not merely stale — is `400`. `[PLAN]` `actions` is a closed union of `{rel, href, method}` with `rel` from a frozen list and `href` server-constructed from pinned ids. A test enumerates every emitted action and fails on any executable path, command, credential, environment blob, merge verb, or spending field (`design:431`).

### 3.5 Lease, report sequence, and the claim/report DTOs

`[SPEC]` Design 410: Desktop claims leased work and sends sequence-checked run reports over `/api/v1`; it never opens the VM store or infers completion from its local process alone. Design 428: claim/renew/report compare lease version, and reports also compare a monotonic per-run sequence. Design 459: a report is an append of `started | event | gate-opened | completed | failed` and **cannot respond to or resolve a human gate**. Design 629: Desktop reports with node-derived host, lease revision, and sequence, and has no human-response transition.

`[PLAN]` Claim takes nothing the client chooses: body is `{waitMs}` with `waitMs ≤ 25000`. **That bound is reconciled with the server's own timeout by the mechanism that exists** [P6-C45, P6-C51]: `index.ts:184` builds `Fastify({ logger: false })` with no `requestTimeout`, and Fastify's `requestTimeout` is a **factory/server-level** option with no plugin- or route-level form — so W6.1 installs **`request.raw.setTimeout(35_000)`** in the node scope's `onRequest` hook, per request, and **leaves the server-level `requestTimeout` untouched**: raising it globally would hand every operator request the long-poll's budget to pay for one route's behaviour. A test asserts a 25-s claim completes and that `index.ts:184`'s factory options are unchanged. **Claims are concurrency-unbounded by the budget** [P6-C65]: 4 per 60 s permits four in flight at once, and a rate budget is not a concurrency limit — the plan makes no "at most one outstanding claim" claim. Correctness comes from the store instead: the claim CAS serialises concurrent claims, so N of them produce exactly one lease row and N-1 refusals (§3.5's split-brain test).

`[PLAN]` **Expired leases are reclaimed by two named runtime mechanisms, not by boot alone** [P6-C36]. Boot reconciliation stays, but it is not the mechanism: (1) **claim-time lazy expiry** — every claim, inside the same CAS transaction and before it selects anything, releases every lease whose `expiresAt` has passed, so a reclaimed run is a candidate for the very claim that reclaimed it; and (2) a **60-s sweeper timer** on the VM daemon that does the same release for runs nobody is claiming, and also expires `v1Idempotency` rows (§3.4). Both emit exactly one durable event per released lease and are idempotent: running them concurrently, or replaying either, releases each lease once. W1 owns the store-side release and the sweeper; W5 owns the client's retry after a `409 lease-expired`. The `expired-lease` probe asserts the run becomes claimable again **exactly once**, and `lease-expiry-reclaim` asserts exactly one owner survives.

`[PLAN]` The server selects the oldest unplaced run already assigned to that host by §3.2 — where "unplaced" now includes a run whose lease the same transaction just reclaimed — CAS-creates the lease inside one store transaction, and returns `{runRef, lease, launchPlan}` or `204` on timeout. Renew takes `{expectedLeaseRevision}`. Report takes `{expectedLeaseRevision, sequence, kind, payload}` and requires `sequence === lastReportSequence + 1`; anything else is `409 report-out-of-order` with **no** state change. `[PLAN]` Reports drive the **same** store transitions the VM-local execution path uses — there is no host-report-only lifecycle and no second projection. `gate-opened` opens a `HumanRequest`; the response to it is the operator's and travels the human-response route only. `completed`/`failed` on an already-terminal run is `409 run-already-terminal` and leaves `terminalOutcome`/`completedAt` untouched (`design:635` "duplicate completion"). The report decoder is an exact-key wall that rejects any `decision`, `expectedRequestRevision`, or assertion-shaped field before any store write.

### 3.6 T3 refusal and the host ban on human response

`[SPEC]` Design 448: T3 kinds require a pinned WebAuthn authorization and a deployment without that ceremony returns `403 ceremony-unavailable`; host node identities are forbidden. Design 191: `approval`, `review`, and `governance-refusal` are the T3 gate kinds; `input` and `intervention` use the ordinary operator channel. Design 528: missing ceremony refuses and never downgrades.

`[PLAN]` `/api/v1/runs/:runRef/human-requests/:requestRef/respond` is a thin caller of the existing `control/humanResponse.ts#respondHumanRequest:34`, reusing P5's T3 binding with `subject:'human-request'` and a preimage over request ref, request revision, response digest, action, origin, and expiry. The refusal ladder is P5's, unchanged: no RP origin or no provisioned credential ⇒ `403 ceremony-unavailable`; wrong preimage/revision/digest ⇒ `403 ceremony-mismatch`; replay ⇒ `409`; no assertion on a T3 kind ⇒ `403 ceremony-unavailable`. A node identity is `403 host-response-forbidden` **before** the ceremony is even consulted, so a host can never burn an assertion.

### 3.7 Builder declaration fields and source-native serialization

`[SPEC]` Design 381: the builder is form-first, assigns existing tools, MCP connector/tool grants, skills, and symbolic filesystem roots, and **does not expose or write a `needs` field**; the server materializes the current `agents/*.md` or `orgs/*/workflows/*.md` schema through the durable PR path. Design 383: agent declarations keep the keys parsed by `readDeclaredAgentDetails` and add optional `group: system`, `connectors: [{server, tools}]`, and `filesystem-roots: [<symbolic-root-id>]`; workflow definitions keep `project`, `profile`, `readScope`, `stages` and add top-level `tools`, `connectors`, `skills`, `filesystemRoots`; builders serialize keys in those source-native casing conventions and reject unknown connector tools/root ids.

`[PLAN]` The two casings are a contract, not a style: agent frontmatter uses hyphenated `filesystem-roots`, workflow frontmatter uses camelCase `filesystemRoots`, and one round-trip test per source proves a parse-then-serialize cycle is byte-identical. "Unknown" is defined against the **union of fresh host advertisements** at edit time, so the builder cannot assign a connector tool or root id no host can serve; the refusal is `422 unknown-connector-tool` / `422 unknown-root-id` naming the offending id and nothing else. A declaration that already carries a `needs` key is read and preserved verbatim but is never written or surfaced by the builder.

Each probe's assertion: **missing-auth** — every `/api/v1` route with no operator subject and no node header is `401` before any store read. **forged-proxy-header** — a request carrying `Tailscale-Node-ID` whose loopback peer uid is not `DASHBOARD_NODE_PROXY_UID` is `401 untrusted-peer`; a request through the proxy carrying a *client-supplied* `Tailscale-Node-ID` **or a forged `X-Forwarded-For`** is refused because the proxy stripped both and resolved its own socket peer instead; a request carrying `Tailscale-User-Login` through the **node** proxy never yields an operator subject, because that proxy mints no user identity at all; and then **two steps under this one id, because a dead proxy and a dead shim are different failures** [P6-C61]: **(a)** with `kb-node-proxy` stopped, W6.3's fixture's **simulated** 8444 listener answers `502` itself and forwards nothing [P6-C70], and the assertion is exactly what that proves — **no dashboard-emitted `503`, and 443 answers `200`**; **(b)** with the proxy up and `kb-whois.service` stopped, the node routes answer **`503 node-attribution-unavailable`** while 443 still answers `200`. Step (a) fails on any dashboard-emitted `503` or a 443 answer other than `200`; the real-listener version of it is P7's [P6-C61]. **forged-node-id** — a well-formed node id absent from the map is `403`, and the response body names no map contents. **revoked-node-id** — a node id in `revoked` is `403 node-revoked`, and at boot its leases are released exactly once. **wrong-host-object** — the Desktop node calling `PUT /api/v1/hosts/vm`, renewing a VM-held lease, or reporting on a run leased to VM is `403 wrong-host`. **operator-calls-daemon-route** — the authenticated operator calling advertise/claim/renew/report is `403 operator-not-a-node`. **host-attempts-human-response** — a node identity calling the respond route is `403 host-response-forbidden`, and a `report` whose payload contains a decision, `expectedRequestRevision`, or assertion field fails the exact-key wall before any store write. **wrong-kind-etag** — a Run ETag presented on a schedule item, a list watermark presented as `If-Match`, and a Health watermark presented as a precondition are each `412`, never a silent success. **stale-cursor** — a cursor minted under an older watermark is `409 cursor-stale` and the client restart yields no duplicate row. **changed-idempotency-replay** — the same key with a changed canonical body is `409`; with an identical body it replays the original status and bytes; **and the probe asserts the three node heartbeat exemptions** [P6-C69, P6-C80]: `PUT /api/v1/hosts/:hostId`, `POST /api/v1/runs/:runRef/leases/renew`, and `POST /api/v1/runs/:runRef/reports` are accepted with **no** `Idempotency-Key` and write no `v1Idempotency` row, a replayed advertisement and a replayed renew are each a no-op **by CAS** (the `host:<hostId>:<version>` ETag / `expectedLeaseRevision` is unchanged and the row is byte-identical) rather than by key, and a replayed report is `409 report-out-of-order` **by sequence** rather than by key. **out-of-order-report** — `sequence ≠ lastReportSequence + 1` is `409 report-out-of-order` with no state change. **duplicate-completion** — a second `completed`/`failed` on a terminal run is `409 run-already-terminal` and `terminalOutcome`/`completedAt` are unchanged. **out-of-order-gate** — a `gate-opened` report after the run is terminal, or a second open of the same request ref, is refused. **expired-lease** — renew or report past `expiresAt` is `409 lease-expired`, and the run becomes claimable again **exactly once** across both reclaim mechanisms: the probe runs the 60-s sweeper and a concurrent claim-time lazy expiry against the same lease and asserts one release event and one new owner [P6-C36]. **lease-theft** — the Desktop node renewing or reporting under another node's lease is `403 wrong-host` even with a correct revision. **false-capability** — a host advertising a connector/skill/root it cannot serve still cannot be selected for a requirement whose canonical hash differs, and a run whose `capabilityHash` no longer matches the advertisement is not dispatched. **stale-advertisement** — an advertisement older than the freshness window is not a candidate; the launch refuses `no-complete-placement` rather than placing on a dead host. **split-brain** — two concurrent claims for the same run produce exactly one lease row and one `409`, proved by a fixed-seed concurrent CAS test. **oversized-unknown-input** — an advertisement over any §3.1 bound (>64 connector servers, >128 tools each, >256 skills, >64 roots) is `413` and is **not** truncated; an unknown key anywhere in any v1 body — advertisement, claim, renew, report, or operator mutation — hits the exact-key wall and is refused `400 unknown-key` **before any store read**, with the refusal naming the offending key and nothing else. This is design 529's oversized/unknown-input clause, which had no probe in r1 [P6-C35]. **node-flood** — a node driven **above** its own budget (claim 4/60 s, renew 6/120 s, report 60 burst then 10/s [P6-C52]) gets `429` **for that node only**, while a concurrent operator write to `/api/control/*` still succeeds and the operator guard's counters are unchanged; the probe fails if the operator surface locks out, and separately if a client staying **within** those budgets is ever throttled [P6-C33]. **capability-loss** — a host that re-advertises without a capability its live lease's `capabilityHash` requires gets `409 capability-lost` on its next renew, the lease is released with exactly one durable event, the run is re-placed **once**, and it is never dispatched to a partial host; this is design 635's own clause, which had no id of its own before r3 [P6-C50]. **node-route-only / operator-route-only** are asserted inside `forged-proxy-header` and `operator-calls-daemon-route` respectively, since both are peer-uid refusals of an existing id's clause [P6-C46].

## 10. Risks + mitigations

| Risk | Mitigation/evidence |
|---|---|
| **Store migration and lease recovery are the highest data-integrity risk** (`design:637`). | W1 follows the P2/P3 migration pattern exactly: back up under the writer lease, migrate in one transaction, quarantine on any per-record failure, and abort startup with a bounded mapping report rather than guessing. The three new collections default to empty on a pre-P6 document [P6-C48], so a read of an unmigrated document is lossless. Boot reconciliation releases every lease whose node id is revoked or whose `expiresAt` has passed, emitting one durable event each; the test replays a crash between claim and first report. |
| **Proxy node attribution or the root map fails open during rotation** (`design:637`). | The map loader fails closed: any malformation, duplicate active id, non-root ownership, or missing file disables advertise/claim/renew/report with `503 host-map-unavailable` while leaving the operator surface up and a Health row visible. `Tailscale-Node-ID` is accepted only behind a peer-uid/full-4-tuple proof against the **separate** `DASHBOARD_NODE_PROXY_UID` [P6-C27] — and separateness is enforced, not assumed: `assertAuthModeBoot` and `validate_vm_runtime.py` both enforce `DASHBOARD_NODE_PROXY_UID ∉ {0, DASHBOARD_TAILNET_PROXY_UID}` — the whole of the D1 fix — so the r3-D1 config *value* that would have let any tailnet client send the header fails the boot [P6-C60, P6-C73]. Pinning `DASHBOARD_TAILNET_PROXY_UID` to `0` is a misconfiguration tripwire beside it, not a second control. The proxy strips every inbound `Tailscale-*` **and `X-Forwarded-*`** header, resolves its own socket peer, and injects only the node header [P6-C19]. The `WhoIs` shim it depends on is bounded (64-byte request, 4 KiB reply, 1 s deadline, 10 in flight) and answers only `GET /localapi/v0/whois?addr=`, so a shim failure is a `503`, never an attribution guess [P6-C47]. `403` bodies name no map contents. **A user login can never substitute for a node id**: the two are separate authenticators on separate hooks — the daemon routes never read `tailscale-user-login`, the operator routes never read `Tailscale-Node-ID` — and `operator-calls-daemon-route` and `host-attempts-human-response` assert both directions. |
| **The node proxy itself becomes an unattested root of trust, or a new SPOF in front of Daniel's dashboard** (r1 blocker 1). | It is neither, by construction [P6-C19]: it ships **inside** the attested release (`deploy` is already a `RELEASE_ROOT`) and is digest-verified at boot; it runs as `kb-node-proxy` under a directive-frozen unit; it mints **node identity only** and never writes `Tailscale-User-*`, so it cannot forge the operator subject; and it sits behind a **second `tailscale serve` listener whose only backend it is**, with the split enforced by peer uid rather than by a path prefix that could not exist [P6-C46], so killing it degrades **only** the node path while the operator surface — which never traversed it — keeps answering. The degradation is stated by which process died [P6-C61]: proxy dead ⇒ `tailscale serve` answers its own upstream error on 8444 and the dashboard emits nothing; shim dead ⇒ `503 node-attribution-unavailable` from the dashboard. Both steps are asserted under the `forged-proxy-header` probe. **It also holds no tailnet rights at all**: `WhoIs` comes from a root-owned shim over a `0660 root:kb-node-proxy` socket, and boot validation fails if `/usr/bin/tailscale debug prefs` reports any `OperatorUser`, so the proxy cannot reconfigure `tailscale serve` [P6-C47]. |
| **A node's traffic — or a hostile node — locks Daniel out of the write surface** (r1 blocker 10); **or the node budget throttles the node client it was written for** (r2 defect 6). | Node routes are metered on their own guard instance with their own budget, never the operator's 30/min mutation budget [P6-C33], and the budget is sized **above** the intended traffic — claim 4/60 s, renew 6/120 s, report 60 burst then 10/s — so an immediate re-claim after a 25-s long-poll and four renewals plus retries per 120-s lease all fit [P6-C52]. The `node-flood` probe fails if a throttled node degrades a concurrent operator write, and separately if in-budget traffic is throttled. |
| **An expired lease is never reclaimed because the VM never restarts** (r1 blocker 13). | Reclaim is a runtime mechanism, not a boot one: claim-time lazy expiry inside the same CAS plus a 60-s sweeper, both idempotent, both W1-owned [P6-C36]. The `expired-lease` probe runs them concurrently against one lease and asserts exactly one release and one new owner. |
| **Per-kind revision domains collapse into one counter** (`design:637`). | The six domains are separate branded TypeScript types with no mutual assignability; there is no generic `compareRevision` helper, and W0's compile-negative vectors fail if a Run ETag is passed where a schedule watermark is expected. `wrong-kind-etag` proves it on the wire. |
| **Capability names drift between declaration, advertisement, and requirement.** | Normalisation happens exactly once, at declaration read, and the stored form is already canonical; a property test asserts idempotence and that `normalize(normalize(x)) === normalize(x)` for the full charset, and the match function refuses any non-canonical input rather than normalising again. |
| **Two implementations appear because `/api/v1` and `/api/*` coexist** (`design:435,500`). | Existing routes become thin adapters in W6.2 and the parity suite asserts the same refusal/success matrix for both URLs; §9 probe 1 allowlists exactly the launch service and the store. Two URLs may coexist; two implementations or stores may not. |
| **P6 lands before P3/P4/P5 and forces a compatibility layer.** | P6-C26 makes P3, P4, and P5 hard scheduling predecessors: W6.1's inbox, deployment, and asset-pull v1 arms are thin callers of services those phases own. W6.1 blocks rather than writing an adapter, which design 500 forbids outright. |
| **The two-daemon fixture drifts from a real two-host deployment, or the LocalAPI grant ships unverified** (r2 defect 7). | Section 8 names exactly what the fixture may not prove and assigns it to Daniel/P7, and the WSL oracle now executes the `WhoIs` shim against a fake tailscaled socket so the grant mechanism is not among those items [P6-C54]. The fixture uses the production `registerV1Routes`, the production node-identity hook, and the production store — only the node map path, the LocalAPI `WhoIs`, and the transport addresses are injected. |
| **A Desktop report becomes a second run lifecycle.** | Reports call the same store transitions the VM-local execution path uses; there is no host-report-only state. A test asserts a Desktop-reported run and a VM-local run produce identical `Run` records apart from `executionHost`. |
