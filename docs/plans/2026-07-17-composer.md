# Composer — Implementation Plan (TDD, chunk-ordered)

The creation flow behind the sidebar **[+ New ▾]** menu. Composer opens a chat session seeded with a
creation template (schema + house conventions + goal); the operator iterates in tandem with the model;
**"deploy"** is a *governed save through branch discipline* → the artifact registers → appears in its
list view. Idea-first is the primary flow.

> **Why this plan reuses so much.** The chat backend, the governed-write discipline, the card path, and
> the routing controls all already exist and are merged. Composer is mostly *wiring an existing dormant
> surface into a convergence flow* + a small multi-turn extension — not new infrastructure. Every place
> this plan invents something new is called out, and the four highest-leverage judgment calls are in
> **§Flagged choices for Daniel**.

## Binding decisions folded in (from Daniel, 2026-07-17 — do not relitigate)

1. **Idea-first is the PRIMARY flow.** Composer starts from a blank idea and converges to a typed
   artifact (Task · Workflow · Skill · Project · Agent) through iteration. The `[+ New]` menu already
   leads with a freeform **"Idea…"** entry (`src/nav/config.ts:116`). Entity-specific pickers are
   *secondary* entry points into the *same* flow (they pre-seed the type; the idea entry does not).
2. **Composer uses the existing Vibe CHAT surface, NOT a PTY.** The terminal/PTY is D3 (the `terminal`
   nav item is a greyed "soon — D3" stub, `src/nav/config.ts:77`). Composer is a chat box, not a shell.
3. **A Composer artifact is a reviewable git commit, never a DB blob.** Deploy = governed write through
   branch discipline.
4. **"+ New → Task" already works day one** via the existing governed launch-card path
   (`LaunchControls` → `POST /api/write/launch`). Composer must not regress it.
5. **All writes go through the existing WebAuthn-gated governed-write discipline** (`server/write/` +
   `server/vibe/`). Composer adds NO new auth surface and NO new audit sink.

## Ground truth (verified in the worktree — trust these over any older prose)

The task brief calls the Vibe surface "dormant/unrouted." That is **half true**, and the distinction
drives the whole plan:

- **The Vibe BACKEND is live and merged.** `POST /api/vibe` is mounted in `server/http/surface.ts:68`
  (`registerVibeRoutes(scope, ctx)`) and streams NDJSON frames from `server/vibe/session.ts#spawnVibe`.
  `spawnVibe` shells **`claude --print --output-format stream-json`** as a CLI subprocess
  (`defaultVibeSpawner`, `session.ts:79`) that **inherits `process.env` verbatim with NO env override** —
  so `ANTHROPIC_API_KEY` stays unset, subscription billing per CLAUDE.md. This is *already* "a Claude
  Code session/runner mechanism, not a raw API key." **The model backend Composer needs already exists.**
- **The Vibe FRONTEND is dormant.** `src/views/Vibe.tsx` exists but is **not** routed in `App.tsx` — no
  nav destination, no `ViewBody` case. Today the `[+ New] → Idea…` entry opens a placeholder
  (`ComposerPlaceholder`, `App.tsx:285`), and `handleCreate('idea')` just toggles `composerOpen`
  (`App.tsx:420`). So the UI shell for Composer exists as a stub with the exact seam to fill.
- **`spawnVibe` is SINGLE-SHOT.** It calls `proc.writeStdin(prompt); proc.endStdin()` immediately
  (`session.ts:240-241`) — one prompt, one `claude` process, no conversation. **Iterate-in-tandem needs
  multi-turn continuity, which spawnVibe does not have today.** This is the single biggest feasibility
  gap and is **Flagged choice #1**.
- **The gate chain is authoritative and must not be re-implemented.** Every `spawnVibe` call runs
  `assertFleetRunnable()` (preamble/STOP/API-key/budget) FIRST, then `verifySession()` (WebAuthn),
  then a per-operator rate-limit/lockout, and writes **exactly one audit row** regardless of outcome
  (`session.ts:168-244`). Composer reuses this verbatim.

## Ordering law (binding on the whole plan)

1. **Reuse the gate chain; never rebuild it.** Every Composer write goes through the *existing*
   `spawnVibe` (chat) / `launchCard` (Task) / `governedSave` (durable) modules, which each independently
   re-run the preamble gate, re-verify the WebAuthn session, and write their own audit row. Composer code
   is *composition + a convergence UI*, never a new gate.
2. **Frozen files are untouchable.** `server/auth/challenge.ts` and `scripts/webauthn_verify.py` are
   **FROZEN** — no Composer chunk may edit, import-and-wrap, or re-implement them. Composer authenticates
   only through the already-merged `verifySession()` seam that the write/vibe modules expose. This is an
   explicit non-goal (see §Non-goals) and a review checkpoint on every chunk.
3. **The credential ceiling holds.** Composer handles no credential as an object. The `claude` child
   inherits ambient env; `ANTHROPIC_API_KEY` stays unset (a precondition the preamble gate already
   enforces). No Composer chunk sets, reads, or prints it.
4. **Durable vs coordination is decided by `classifyTarget`, not by Composer.** Composer picks the
   *relpath*; `branch.ts` decides the branch. A Task → `queue/**` → `ops`; a Skill/Workflow/Project →
   durable → PR to `main`. Composer never direct-pushes `main` or `ops` (`PROTECTED_BRANCHES` denylist
   in `branch.ts:84` is the backstop).
5. **Idea-first drives the state machine.** The convergence UI's initial artifact type is
   `unknown` ("an idea"); the type is *resolved during the conversation*, not required up front. Entity
   pickers are the same machine pre-seeded.

**Branch discipline (per CLAUDE.md).** All Composer code lands on `claude/*` work branches → **PR to
`main`**. Runtime writes Composer triggers are governed by the reused modules: a Task card is
**coordination** (`ops` pull-rebase-push); a durable artifact is a **work-branch → PR to `main`**. No
Composer chunk writes `governance/` or `CLAUDE.md` (human-only).

# The architecture

## A. The idea-first chat: seeding + streaming

**Backend (reuse + one extension).** Composer's chat talks to the **existing** `claude --print
--output-format stream-json` subprocess path via `spawnVibe`. Nothing about the *model backend* is new:
no API key, subscription billing, full gate chain. The ONE thing missing is **multi-turn continuity**,
because `spawnVibe` ends stdin after the first prompt (`session.ts:241`).

The realistic, low-risk extension (Flagged #1, recommended option A): thread the CLI's own session id.
`claude --print --output-format stream-json` emits a `system` init record on stdout whose payload carries
the `session_id`. Today `foldRecords` *drops* `system` from the **timeline model** (`SKIP_RECORD_TYPES`,
`record.ts:40`) — but `spawnVibe`'s `onStdout` still receives every raw line before the fold. A thin
`composer/session.ts` wrapper captures that `session_id` from the raw stream and returns it to the client;
each subsequent turn re-invokes the same governed spawn path with `['--print','--output-format',
'stream-json','--resume',<session_id>]`. Each turn is still a discrete, independently-gated,
independently-audited spawn — the rate-limit/lockout model (`session.ts:107`) stays intact (a turn ==
a spawn). No long-lived process, no interactive-stdin re-architecture, no change to the frozen auth path.

**Seeding.** When Composer opens, the first turn's prompt is composed **server-side** from a house-authored
*creation template* for the resolved artifact type (§B) + the operator's idea text. The template is inert
house context (schema + conventions + the deploy contract), NOT untrusted external text — the operator's
own live session is already the RCE-equivalent Vibe threat model, so the `## Evidence` inert-data rule does
not newly apply here; the seed is trusted scaffolding the operator could have typed themselves. The seed is
never sourced from a card body or scraped text.

**Streaming.** Reuse the *entire* existing stream path unchanged: `defaultVibeStream` (`Vibe.tsx:49`) POSTs,
reads the NDJSON body, parses each line with the shared `parseRecord`, folds with `foldRecords`, and renders
through the shared `Timeline` component. Composer's chat pane **is** the Vibe view, re-parented into the
Composer surface, plus a per-turn prompt box (multi-turn) instead of a one-shot form.

## B. The convergence mechanic: freeform idea → typed artifact draft

A pure, testable **type registry** (`src/composer/artifactTypes.ts`, new, no I/O) is the spine. For each of
`task | workflow | skill | project` it declares:

- **`seedTemplate(idea)`** — the house-authored creation prompt (schema shape + conventions + the deploy
  contract for that type). Idea-first: `unknown` has a *disambiguation* seed that asks the model to help
  the operator decide which type the idea wants to become.
- **`draftSchema`** — how to validate a proposed draft before deploy:
  - **Task** → the fields `launchCard` needs (`project`, `action`, `target`, `riskTier`, `body`) — the
    same set `LaunchControls` collects; server-side truth is `scripts/cards.py#_validate`.
  - **Skill** → `SKILL.md` with `name` + `description` frontmatter (the two fields `registry/skills.ts`
    reads) + a Markdown body.
  - **Workflow** → filename `wf_<name>.md` (the registry derives `id` from the filename; there is no
    frontmatter schema today — validate the filename shape + non-empty body).
  - **Project** → the four template files rendered from `templates/*` with `{{name}}`/`{{date}}` filled.
- **`toDeploy(draft)`** — maps the validated draft to `{ kind, relpath(s), content(s), branchHint }` for
  the deploy dispatcher (§C).

**Convergence UI** (`src/composer/Composer.tsx`, new — replaces `ComposerPlaceholder`):

1. A **type chip** starting at `idea` (unknown). As the conversation progresses the operator (or a model
   suggestion the operator confirms) sets the concrete type; setting it swaps in that type's seed on the
   next turn. Secondary entity pickers (`[+ New] → Skill`, etc.) start the chip pre-set.
2. The **chat pane** (§A) — iterate in tandem.
3. A **draft preview panel**: the operator (or model) proposes a draft; Composer renders the exact
   file(s), the **target relpath**, the **branch class** ("durable → PR to main" / "coordination → ops"),
   and any **schema-validation** problems inline. Deploy is disabled until the draft validates.

## C. Deploy: governed write per artifact type

Deploy is a **thin dispatcher** (`src/composer/deploy.ts`, new — client fetch layer only) that maps the
validated draft's `kind` to the **existing** governed endpoint. It never writes files, never chooses a
branch, never re-implements a gate:

- **Task** → `POST /api/write/launch` with `{project, action, target, riskTier, body}` (exactly what
  `LaunchControls` sends). Server files a `queue/<ulid>.md` card via `launchCard`. **Works day one; zero
  new server code.**
- **Skill / Workflow / Project** → `POST /api/write/save` with `{relpath, content, message}`. `governedSave`
  confines the path, refuses `governance/**` + constitution files (403), writes, and routes durable →
  work-branch → **PR to `main`** (`governedSave.ts:67`, `routeDurable`). The server owns the work branch
  (client-supplied `workBranch` targeting `main`/`ops` is hard-rejected 403, `routes.ts:73`).

For a Task, Composer may additionally offer the **existing** `RoutingControl` (`views/routingControls.tsx`)
so the operator sets a per-card `runtime`/`model` at creation via the already-governed
`POST /api/write/card-routing` — pure reuse, optional.

Multi-file durable artifacts (Skill dir, Project's four files) need multiple `save` calls or a multi-file
governed write — **Flagged #2**.

# Flagged choices for Daniel

**#1 — Multi-turn chat: `--resume` per turn (recommended) vs. a long-lived interactive process.**
`spawnVibe` is single-shot (`session.ts:241`). Composer needs conversation. **Recommended (A):** each turn
is a fresh, independently-gated `spawnVibe` spawn re-invoked with `--resume <session_id>`, where the id is
captured from the CLI's `system` init record (the fold already discards it from the *timeline* but raw
stdout still carries it). Keeps the rate-limit/lockout and one-audit-row-per-spawn model exactly as merged;
no frozen-auth change. **Alternative (B):** one long-lived `claude` process with interactive
`--input-format stream-json` stdin — fewer process spawns but breaks the per-spawn rate-limit accounting
and turns the audit trail into one row per *session* instead of per *turn*, and needs new lifecycle/stop
wiring. **Decision:** confirm A, or accept B's different gate/audit granularity.

**#2 — Multi-file durable artifacts vs. single-file `governedSave`.** `governedSave` writes one relpath per
call (`governedSave.ts:67`). A Skill is a directory (`SKILL.md` + `references/*`) and a Project is four files
+ subdirs. **Recommended:** v1 deploys the **primary file only** (`SKILL.md` / `orgs/<n>/_index.md` /
`wf_<n>.md`) and the operator iterates additional files as follow-up saves in-session — ships fast, each
file is an independently reviewable commit. **Alternative:** build C6's atomic `save-many` so a Skill/Project
lands as one commit/PR. **Decision:** primary-file-first v1, or invest in atomic multi-file now.

**#3 — Which skill tier Composer deploys to (the `sync_skills` hook).** The `.githooks/pre-commit`
`sync_skills` gate mirrors `skills/curated/` → `.claude/skills` and **blocks the commit on drift** — and
`governedSave` deliberately keeps hooks active (never `--no-verify`, `branch.ts:20-21,50-57`). A Composer
save into `skills/curated/**` therefore fires that gate mid-commit. **Recommended:** Composer skills land in
**`skills/learned/`** (not mirrored/synced), and a human promotes to `curated` later — Composer never trips
the sync gate. **Alternative:** target `curated` and let the hook self-heal (it runs `sync_skills.py` + `git
add .claude/skills` during the commit), accepting the added failure surface. **Decision:** learned-tier
default, or curated-with-hook.

**#4 — "Agent" has no clean governed on-disk home.** The Agents roster is *derived from card ownership*
(`roster.ts` groups cards by `owner:`); an agent's behavior lives in `routines/roles/*.md` (durable) and its
routing in `governance/model-routing.yaml` (**human-edited only** — agents propose in `docs/proposals/`).
There is no agent-object file to "deploy." **Recommended:** Composer's **Agent** entry stays **disabled in
v1**; when built, "+ New → Agent" produces a **proposal** under `docs/proposals/` (a role-prose draft + a
proposed routing-policy diff) for Daniel to commit — never a direct governed write into `governance/` or a
fake agent identity. **Decision:** defer Agent to a proposal-doc path, or design a first-class agent registry
(bigger scope, out of this plan).

# Explicit non-goals

- **No PTY / terminal.** That is **D3** (the `terminal` nav item stays a greyed "soon — D3" stub). Composer
  is a chat surface only.
- **No new auth surface.** Composer authenticates exclusively through the already-merged `verifySession()`
  seam the write/vibe modules expose. It mints no sessions of its own and adds no login chrome.
- **Frozen files untouched.** `server/auth/challenge.ts` and `scripts/webauthn_verify.py` are **FROZEN** —
  no Composer chunk edits, imports-and-wraps, or re-implements them. This is a hard review checkpoint on
  every PR in this plan.
- **No `governance/` or `CLAUDE.md` writes.** Human-edited only; `governedSave` already refuses them (403).
  The Agent artifact's routing lives here, which is exactly why Flagged #4 routes it to `docs/proposals/`.
- **No raw API key.** `ANTHROPIC_API_KEY` stays unset; the `claude` child inherits ambient env with no
  override. Subscription billing only. No Composer chunk sets/reads/prints it.
- **No direct push to `main` or `ops`.** Durable Composer writes are work-branch → PR to `main`;
  coordination (Task cards) are `ops` pull-rebase-push — both via the existing modules, with the
  `PROTECTED_BRANCHES` denylist as the backstop.
- **No new audit sink.** Every Composer write reuses a module that already writes exactly one audit row.

# Exit criteria

- `[+ New] → Idea…` opens Composer in idea mode; the operator iterates with a real, gated, multi-turn

- Secondary entity pickers pre-seed the same flow; **Agent** stays deferred per Flagged #4.
- Frozen auth files untouched; `ANTHROPIC_API_KEY` unset throughout; all writes governed; `vitest run` +
  `tsc --noEmit` green on every chunk PR.
