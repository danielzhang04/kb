`[SPEC]` is fixed by the cited design or movement spec. `[PLAN]` closes a choice the specs leave open. W0 makes every type and vector below compile before any behavior work.

### 3.1 Deployment Inbox item and action union

`[SPEC]` The item shape is design 256 verbatim: `{kind:'deployment'; subject:{deploymentRef}; title; state; blockingPtyIds: string[]}` over the `InboxBase` of `design:249-253`. `[PLAN]` `state` is the closed union `DEPLOYMENT_STATES` (`deploymentState.ts:12-22`) plus `'deploy-ready'` [P5-C17]; `deploymentRef` is either a stored `Deployment.deploymentRef` or the derived `deploy-ready:<40 lowercase hex>`. `id = sha256("deployment" + "\0" + deploymentRef)`, matching P4 §3.3's ID rule. `revision` is the store `Deployment.revision` for a record, and `sha256(targetSha + "\0" + liveSha)` for a deploy-ready subject. `blockingPtyIds` is the sorted unique set of live PTY session ids from the P3 registry snapshot, each matching `/^pty-[0-9a-f]{32}$/`; it is empty for every non-`parked` state.

`[PLAN]` The action is the total single-valued function of P5-C18:

| Condition (evaluated in order) | Action | T3 | Endpoint |
|---|---|---|---|
| `blockingPtyIds.length > 0` | Close PTYs and continue | yes | `POST /api/inbox/deployment/:ref/close-ptys-and-continue` |
| `state === 'waiting-confirmation'` | Confirm | yes [P5-C21] | `POST /api/inbox/deployment/:ref/confirm` |
| `state === 'deploy-ready'` | Deploy | yes | `POST /api/inbox/deployment/:ref/deploy` |
| `state ∈ {requested,parked}` and `abortRequestedAt === null` | Abort | yes | `POST /api/inbox/deployment/:ref/abort` |
| `state ∈ {requested,parked,swapping,resuming}` otherwise | Inspect | no | GET navigation to Health `daemon-machine#deploy:<ref>` [P5-C19] |
| `state ∈ {succeeded,aborted,failed}` | Acknowledge | no | `POST /api/inbox/deployment/:ref/acknowledge` |
| `state === 'acknowledged'` | — item absent | — | — |

`[SPEC]` Lifecycle is design 266: the item changes action with its canonical Deployment state and vanishes only after terminal Acknowledge. `[PLAN]` Deploy and Confirm on a `deploy-ready` subject call `store.ts#createDeployment` with `initialState` per P5-C17 and are idempotent on `idempotencyKey = "deploy:<targetSha>"`; every other action calls `store.ts#transitionDeployment` with the pinned `expectedRevision` and `expectedState` the item carried. A stale revision is `409` with no helper invocation. **No P5 code contains a second deployment transition path**: `control/store.ts#transitionDeployment` stays the sole mutator, and §9 probe 3 enforces it.

`[SPEC]` Design 371: a deploy-ready item is projected **only** when tested green `main` is strictly newer than the immutable VM live release. `[PLAN]` The projector requires all of: the release reader reports an available live SHA; `main`'s tested-green head is a strict descendant of it; and no non-terminal Deployment exists (the store already refuses a second active one at `store.ts:3677`). Any unmet condition yields no item, never a disabled one.

### 3.2 Asset-pull intent record and Inbox item

`[SPEC]` movement 256 fixes the record verbatim: `AssetPullIntent = {intentRef,runRef,manifestDigest,state,requestedAt,attempts,result}`, created only for a succeeded run with a stored manifest digest, and the endpoint never pretends the VM performed the desktop transfer. Design 257 fixes the Inbox subject `{intentRef,runRef,manifestDigest}` and design 266 fixes the lifecycle: a successful pull vanishes on the helper receipt; offline or failure stays visible and retryable.

`[PLAN]` `state` is the closed union `'pending' | 'in-flight' | 'succeeded' | 'failed' | 'offline'`. `manifestDigest` is 64 lowercase hex; `intentRef` is `assetpull-<32 hex>`; `attempts` is a non-negative integer capped at 32; `result` is `null | {outcome:'succeeded'|'failed'; receiptAt; errorCode}` with `errorCode` in the closed union `unavailable|timeout|digest-mismatch|refused|invalid`. The record joins the control-plane document beside `deployments` under the same exact-key discipline (`deploymentState.ts:44-57` is the pattern) and commits at durability `'ordinary'`, not `'deploy-critical'` — an asset pull is not a release transition. Action mapping is total: `pending` ⇒ **Pull home**; `in-flight` ⇒ **Inspect**; `failed`/`offline` ⇒ **Retry**; `succeeded` ⇒ item absent. `id = sha256("asset-pull" + "\0" + intentRef)`. Pull and Retry reuse one idempotency key `pull-assets:<intentRef>:<manifestDigest>` so the resident retry loop of movement 256 resends the same key until the helper reports success or failure.

### 3.3 T3 token binding and refusal

`[SPEC]` design 528: a T3 gate or deploy kind requires a WebAuthn assertion pinned to subject, revision, decision, and digest; a missing ceremony refuses and never downgrades. Design 670: tailnet-only deployments return `403 ceremony-unavailable` and no lower channel exists.

`[PLAN]` The deploy ceremony is a purpose-bound ceremony in the existing `auth/routes.ts` map, following the `:97-99` precedent. Its challenge preimage is the canonical UTF-8 encoding of `kb.deploy-t3/v1\0<subject>\0<ref>\0<revision>\0<decision>\0<digest>`, where `subject ∈ {'deployment','pty-quiescence'}`, `ref` is the `deploymentRef`, `revision` is the pinned Deployment revision, `decision ∈ {'confirm','deploy','abort','close-ptys-and-continue'}`, and `digest` is the target commit's attestation digest for `deploy`/`confirm`, or `sha256(sorted blockingPtyIds joined by "\0")` for `close-ptys-and-continue`. Verification recomputes the preimage server-side from the store record and compares bytes; it never accepts a client-supplied preimage. A grant is single-use, consumed under the same store CAS as the transition, and expires in 120 seconds — deliberately wider than the 5-second execution-unlock window (`activation.ts:194-200`) because a deploy ceremony precedes a bounded network call rather than an in-process wiring construction.

`[PLAN]` The refusal ladder is closed and never downgrades: no RP origin configured, or no provisioned credential for the operator ⇒ **`403 ceremony-unavailable`**; assertion present but preimage, revision, or digest mismatched ⇒ `403 ceremony-mismatch`; assertion replayed ⇒ `409`; no assertion at all on a T3 endpoint ⇒ `403 ceremony-unavailable`. Session authentication alone never satisfies a T3 endpoint, and the browser disables the control while also proving the server refuses it (`design:617`). Error bodies carry a fixed code and no key, signer, challenge, or credential material.

### 3.4 Desktop-helper client and closed payload/result union

`[SPEC]` movement 235 fixes the request union exactly — `deploy {sourceCommit,attestationDigest,requestRef}`, `pull-assets {intentRef,runRef,manifestDigest}`, `deployment-result {deploymentRef,outcome}` — with one deploy request plus a five-minute cooldown, independently idempotent and rate-limited pull/result, and no verb accepting paths, hosts, commands, or keys. Movement 237 fixes the receipt behavior. Design 527 forbids returning signer or key material.

`[PLAN]` `dashboard/server/deploy/helperClient.ts` is the only module in `dashboard/server` permitted to speak the helper protocol. It encodes exactly the three verbs, rejects any extra or unknown field before serialization, and decodes only the closed result union `{verb; requestRef; outcome:'accepted'|'refused'|'failed'; refusalCode?; receiptAt}` with `refusalCode` in `forged-node|forged-source|forged-attestation|unknown-verb|unknown-field|repeat-key|cooldown|stale-revision|active-pty|failed-swap|rollback|misleading-symlink`. Every response is validated by an exact-key wall; an unknown key, an unknown verb echo, or any field resembling a signature, key, or path fails closed as `refused` with `errorCode:'invalid'` and never reaches the store. Transport is a bounded HTTPS call to the pinned desktop tailnet address with a 20-second timeout and no redirects; the VM never learns a helper filesystem path.

`[PLAN]` **Prerequisite byte/schema check (design 667).** Before the first Deploy of a daemon lifetime, the client fetches the helper's advertised protocol descriptor and compares it byte-for-byte against a frozen `dashboard/server/deploy/movementProtocol.json` generated from movement §3. A mismatch **fails closed**: Deploy is not offered, no request is sent, and one deduplicated escalation card is created through the P4 reconciliation publisher. Pull home is likewise offered only after the helper advertises `pull-assets/v1` (movement 256).

### 3.5 Health machine, daemon, release, and deploy rows

`[SPEC]` design 296: `/api/health` composes runtime capability probes, OS CPU/RAM/disk/uptime, immutable release metadata, and the latest Deployment; spend fields are omitted, not zeroed. Design 300: each section has a last-observed time and one failed probe produces an unavailable row without hiding other sections. Design 621: machine probes must be bounded so disk or MCP failure cannot stall Health.

`[PLAN]` The `daemon-machine` section gains four row kinds, all inside the existing `HealthRow` union and all carrying `observedAt`:

```text
MachineRow  = {kind:'machine'; key:'daemon-platform'|'cpu'|'memory'|'disk'|'uptime'; label; value; observedAt; source:'machine'}
DaemonRow   = {kind:'daemon'; key:'service'; label:'Service'; value:{unit; mainPid:number; loadedRoot:string; childCount:number}; observedAt; source:'daemon'}
ReleaseRow  = {kind:'release'; key:'release'; label:'Release'; value:{sha:string; archiveSha256:string; activatedAt:string; rollbackAvailable:boolean}; observedAt; source:'release'}
DeployRow   = {kind:'deploy'; key:`deploy:${string}`; label:'Deployment'; value:{deploymentRef; state; targetCommit; previousCommit; error:string|null}; observedAt; source:'deploy'}
```

The `'daemon-platform'` machine row keeps its current `'win32'|'linux'` value; the four new machine keys carry `{used,total,unit}` for memory and disk, a load triple for cpu, and integer seconds for uptime. `ReleaseRow` replaces the deferred placeholder at `health/service.ts:20` [P5-C14] and is fed by the **same** activation port Home uses (`home/routes.ts:24-42`), never by a checkout read. `DeployRow` is fed by `store.ts#listDeployments` and is the deep-link target of Inspect [P5-C19]; it is a display row and carries no control, honoring ux-rule 11.

`[PLAN]` **Bounded probes are structural, not advisory.** Every new reader is invoked through one shared `withBudget(label, ms, fn)` wrapper with these hard ceilings: cpu/memory/uptime 250 ms, disk 750 ms, release 1000 ms, daemon (`systemctl show` + cgroup walk) 1500 ms, deploy (store read) 250 ms. The wrapper resolves — never rejects — and a timeout, throw, or malformed value yields the existing closed `UnavailableRow` (`health/service.ts:23`) with `reason` drawn from the closed union `timeout|unavailable|invalid`, so a hung disk or an unresponsive `systemctl` can degrade exactly one row. The whole `daemon-machine` composition is additionally wrapped at 2500 ms. Raw `stderr` never reaches a row; spend fields are omitted, never zeroed.

### 3.6 Home version source

`[SPEC]` design 308: the chip format is `VM · 64fb3d02 · 2h ago`, and the SHA and activation time come from immutable live release status, not the checkout symlink or client cache. `[PLAN]` **The reader is already correct and is not rewritten** [P5-C6]. P5's only Home changes are: (a) the `<ago>` is rendered relative to the response's `generatedAt` (`home/contracts.ts:31`), never `Date.now()` in the browser — a P2 W6.x browser fix this plan must not regress; (b) the same `ActivationReaderPort` instance is injected into Health so both surfaces read one release, proved by a test asserting a single reader construction; (c) when the release read fails, the chip stays `{state:'unavailable',reason:'release-unavailable'}` and no other Home section degrades (`home/project.ts:49-53`). No release value is cached across requests.

### 3.7 Quiescence and close-ptys-and-continue

`[SPEC]` design 264: close-and-continue is part of deploy quiescence, pins the exact live session ids and deployment revision, records Daniel as actor, and refuses unless every `closeAndWait` confirms. Design 619 and 673: deploy closes exact live ids only through Daniel's quiescence action.

`[PLAN]` The action takes `{deploymentRef, expectedRevision, sessionIds}` plus the T3 assertion whose digest pins `sha256(sorted sessionIds)`. The server re-reads the live session set and refuses `409 pty-set-changed` if it differs by even one id — it never closes a superset, a subset, or a re-derived set. It then calls the P3 `DeploymentSessionCloser` (`pty/sessionRecord.ts:129`) with exactly those ids. **Any non-`ok` result, including one `closeAndWait` timeout, refuses the whole action** with `409 pty-not-confirmed`, leaves the Deployment revision untouched, and re-projects the item with the still-blocking ids. Only an `ok` result with `closed` equal to the pinned set advances `parked → swapping`, recording `actor:'human-operator'` with Daniel's attribution (`auth/operator.ts:18,64`).

## 9. Adversarial review script

The eleven helper checklist items of design line 619 (three forgery variants, unknown verb/field, repeat key, cooldown, stale revision, active PTY, failed swap, rollback, misleading symlink) are one manifest each and one executable probe each:

```powershell
cd dashboard
$cases = @(
  'forged-node','forged-source','forged-attestation','unknown-verb-or-field','repeat-key',
  'cooldown','stale-revision','active-pty','failed-swap','rollback','misleading-symlink'
)
foreach ($case in $cases) {
  node server/testFixtures/p5FixtureLifecycle.ts --attack $case --artifact-dir ".artifacts/p5-attacks/$case" --assert-isolated
  if ($LASTEXITCODE -ne 0) { throw "P5 attack probe failed: $case" }
}
node server/testFixtures/assertP5GateResults.ts --attack-root .artifacts/p5-attacks --manifest server/testFixtures/p5AttackManifest.json --require-exact $cases.Count
if ($LASTEXITCODE -ne 0) { throw 'P5 attack manifest mismatch' }
```

Each probe's assertion: **forged-node** — a caller whose Tailscale-derived node identity is not the pinned VM is refused before any signer call. **forged-source** — a `sourceCommit` that is not a strict descendant of the live SHA is refused and no request is sent. **forged-attestation** — an `attestationDigest` disagreeing with the archive digest is refused; no partial activation occurs. **unknown-verb-or-field** — an unknown verb, an extra request field, and an extra result key each fail closed with no store write. **repeat-key** — the same idempotency key returns the original receipt and opens no second request. **cooldown** — a second deploy inside five minutes is refused with `cooldown` and no request leaves the VM. **stale-revision** — a transition pinned to an outdated Deployment revision is `409` with no helper invocation. **active-pty** — a deployment with live PTYs offers only `close-ptys-and-continue`, and a `closeAndWait` timeout refuses `409 pty-not-confirmed` while leaving the revision untouched. **failed-swap** — an injected swap failure lands in `failed` with the error retained and only Acknowledge offered. **rollback** — a rollback is a deliberate movement §2.5 transition and is never reachable as an Inbox Abort. **misleading-symlink** — a `current` symlink pointing outside `/opt/kb-releases` is refused by the release reader, which reports unavailable rather than a wrong SHA.

Literal source and absence closure. Every probe is `rg` over the **working tree**, never `git grep`, because nothing in P5 is committed. Exit semantics for all five probes: **0 = matches found**, **1 = no matches**, **2 = probe error** and therefore a throw. Probes 1, 2, and 5 are clean only at exit 1; probes 3 and 4 may exit 0 and are judged by their allowlist filter. The comment filter is exactly `-notmatch '^[^:]+:\d+:\s*(//|\*|/\*)'`, anchored on rg's `path:line:` prefix — never a bare `://`, which would drop every line containing `https://`.

```powershell
Set-Location ..
function Invoke-P5Scan([string]$Label, [string[]]$RgArgs) {
  $hits = & rg @RgArgs
  if ($LASTEXITCODE -eq 2) { throw "P5 scan errored: $Label" }
  if ($LASTEXITCODE -notin 0,1) { throw "P5 scan returned $LASTEXITCODE : $Label" }
  return $hits
}

# 1. No deploy destination, page, or route — expect exit 1.
$deployPage = Invoke-P5Scan 'deploy-destination' @('-n','-e','api/deploy|DeployView|deploy-page|''deploys''','dashboard/server','dashboard/src')
if ($deployPage) { throw $deployPage }

# 2. No checkout-derived release status — expect exit 1.

if ($checkoutRelease) { throw $checkoutRelease }

# 3. Deployment transitions — allowlist is EXACTLY control/store.ts + deploy/deploymentService.ts.
$transitions = Invoke-P5Scan 'deploy-transitions' @('-n','-e','transitionDeployment|createDeployment','dashboard/server')
$transitionCode = $transitions | Where-Object { $_ -notmatch '\.test\.ts:|testFixtures[/\\]' } | Where-Object { $_ -notmatch '^[^:]+:\d+:\s*(//|\*|/\*)' }
$unexpected = $transitionCode | Where-Object { $_ -notmatch 'control[/\\]store\.ts|deploy[/\\]deploymentService\.ts' }
if ($unexpected) { throw $unexpected }

# 4. Helper protocol — only helperClient.ts may name a helper verb.
$helperHits = Invoke-P5Scan 'helper-speakers' @('-n','-e',"'deploy'|'pull-assets'|'deployment-result'",'dashboard/server')
$helperCode = $helperHits | Where-Object { $_ -notmatch '\.test\.ts:|testFixtures[/\\]|movementProtocol\.json' } | Where-Object { $_ -notmatch '^[^:]+:\d+:\s*(//|\*|/\*)' }
$unexpectedHelper = $helperCode | Where-Object { $_ -notmatch 'deploy[/\\](helperClient|contracts)\.ts' }
if ($unexpectedHelper) { throw $unexpectedHelper }

# 5. No T3 downgrade path — expect exit 1 (no deploy endpoint may accept session-only auth).
$downgrade = Invoke-P5Scan 't3-downgrade' @('-n','-e','ceremony[^\n]*optional|skipCeremony|allowSessionOnly|webauthn-unconfigured','dashboard/server/deploy','dashboard/server/inbox')

# 6. Absence inventory — run the section 4 PowerShell assertion here, then:
git status --short
```

Behavior probes, not grep alone, establish: a forged identity never reaches the signer; an extra field never decodes; a repeated key never opens a second request; a cooldown never leaks a request; a stale revision never invokes the helper; an unconfirmed PTY exit never advances a deployment; a failed swap never fabricates success; and a misleading symlink never yields a wrong SHA.

| An asset pull is reported as done by the VM when the desktop never transferred (movement 256). | The intent only ever reaches `succeeded` on a decoded helper receipt; `pending`, `in-flight`, `offline`, and `failed` all keep the item visible and retryable, and W1 tests forbid a VM-side success transition. |
