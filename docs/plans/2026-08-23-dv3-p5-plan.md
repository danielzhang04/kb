### 3.1 Deployment Inbox item and action union

`[SPEC]` The item shape is design 256 verbatim: `{kind:'deployment'; subject:{deploymentRef}; title; state; blockingPtyIds: string[]}` over the `InboxBase` of `design:249-253`, whose `revision` is a **string** (`design:252`). `[PLAN]` `state` is the closed union `DEPLOYMENT_STATES` (`deploymentState.ts:12-22`) plus `'deploy-ready'` [P5-C17]; `deploymentRef` is either a stored `Deployment.deploymentRef` or the derived `deploy-ready:<40 lowercase hex>`, and **the Deployment created from a deploy-ready subject reuses that subject's `deploymentRef` verbatim**, so the id is stable across Deploy [P5-C17]. `id = sha256("deployment" + "\0" + deploymentRef)`, matching `p4-plan:194`'s ID rule.

`[PLAN]` **The `revision` stringify/parse rule** [P5-C28]. `Deployment.revision` is a number; the Inbox item carries the string `deployment:<n>` with `n` the decimal store revision, no padding and no leading zero. All six deployment endpoints — `challenge`, `confirm`, `deploy`, `abort`, `acknowledge`, `close-ptys-and-continue`, there being **no `decline`** [P5-C49] — parse a `deployment:<n>` `expectedRevision` back with the closed parser `/^deployment:(0|[1-9][0-9]{0,15})$/` and refuse anything else — a bare number, a padded number, a foreign prefix, or a value out of range — with `400 invalid-revision` **before** any store read, ceremony verification, or helper call. A deploy-ready subject carries `revision = "deploy-ready:" + sha256(targetSha + "\0" + liveSha)`, which only `deploy`, `confirm`, and the matching `challenge` decision accept and every other endpoint refuses [P5-C58]. **Stated positively per endpoint, and closed both ways** [P5-C47, amended by P5-C58]: `POST …/deploy` accepts **only** the derived `deploy-ready:<sha256>` revision over a `deploy-ready:<40 lowercase hex>` `:ref`, and refuses `deployment:<n>` with `400 invalid-revision` (a created Deployment is no longer deploy-ready, whatever its `:ref` spelling); `POST …/confirm` accepts a **closed two-spelling union** — `deploy-ready:<sha256>` over a `deploy-ready:<40 lowercase hex>` `:ref` (the P5 breaking entry, which creates the record) **or** `deployment:<n>` over a `deployment:<n>` `:ref` (the spec's `waiting-confirmation` arm, which CASes an existing record) — and refuses every other spelling `400 invalid-revision`; `abort`, `acknowledge`, and `close-ptys-and-continue` accept **only** `deployment:<n>` and refuse any `deploy-ready:` revision the same way; `challenge` accepts exactly the spelling its `decision` requires — `deploy-ready:` for `deploy`, either member of the union for `confirm`, `deployment:<n>` for `abort` and `close-ptys-and-continue` — and refuses any other pairing `400 invalid-revision` [P5-C47, P5-C58]. **Verb/candidate agreement is checked after parsing and before any ceremony work** [P5-C58]: a `breaking:true` candidate presented to `/deploy` is **`409 confirm-required`**, a `breaking:false` candidate presented to `/confirm` is **`409 deploy-required`**, and a `deploy-ready:<sha>` whose sha is no longer `DeployReadyPort.latestCandidate().sha` is **`409 revision-changed`** — the code §9's `stale-revision` probe already uses, not a new one; on a `deploy-ready` ref this means the candidate moved on — refetch `/api/inbox`. The `:ref` path segment itself is parsed by one closed matcher, `/^(deploy-ready|deployment):[0-9a-f-]{1,64}$/`, refusing anything else `400 invalid-ref` before the revision is even read.

`[PLAN]` `blockingPtyIds` is the sorted unique set of live PTY session ids from the P3 registry snapshot, each matching `/^pty-[0-9a-f]{32}$/`. **It is the live set at projection time in any pre-swap state of a STORED Deployment, not only `parked`**: `design:264` pins the exact live session ids and never restricts which stored state may carry them, so the r1 narrowing ("empty for every non-`parked` state") stays dropped [P5-C39]. **The one exclusion is `deploy-ready`** [P5-C59]: that subject is a read projection of a release with no Deployment record behind it, so it carries `blockingPtyIds: []` **by construction**, never renders Close PTYs and continue, and never reaches an endpoint that requires a `deployment:<n>` revision. Quiescence is a property of a deployment in flight, not of a candidate.

`[PLAN]` The action is the total single-valued function of P5-C18 — **exactly one MUTATING control per actionable state, matching `design:264`'s "exactly the state-valid action"; Inspect is navigation and is always present alongside it** [P5-C49]:

`[PLAN]` **There is no Decline; `waiting-confirmation` exposes exactly Confirm** [P5-C49]. `design:264` closes the set — "Deployment exposes exactly the state-valid action from Confirm, Deploy, Inspect, Abort, Acknowledge, or Close PTYs and continue" — and `movement:254` fixes the entry verbs: "green becomes Deploy, breaking becomes Confirm, active/failure becomes Inspect". **Neither candidate is materialised as a record before the operator acts** [P5-C58]: green and breaking alike are projected as the derived `deploy-ready:<sha>` subject, the green one offering Deploy and the breaking one offering Confirm, and each handler creates the Deployment at `requested` itself. The stored `waiting-confirmation` state keeps its Confirm arm — `movement:47` lists the state and `movement:106` projects it as "No fence; project Confirm" — so the projector, the action function, and the reconcile switch stay exhaustive over `DeploymentState` (`movement:113`'s `assertNever`), but **P5 ships no writer that puts a record there**, and W3 asserts that too. Live Abort is offered at exactly `movement:115`'s `requested|parked`: "Live Abort is one dashboard CAS allowed only from `requested|parked`: set terminal `aborted`, clear fence/lease epoch and drain acknowledgements, rehydrate or contain every already-paused row through the shared rehydrator, then restart the bridge directly. … Abort is idempotent after success and returns 409 once `swapping|resuming` begins." A direct call to `…/abort` at `waiting-confirmation`, `swapping`, or `resuming` is refused `409`, and the swap states additionally escalate as below. **There is no supersession abort, because there is nothing to abort** [P5-C58]. `deploy-ready` is a **read projection** of `DeployReadyPort.latestCandidate()`: when a newer attested release lands, the older candidate simply stops being projected and its subject disappears from the next `GET /api/inbox` — no record was ever written for it, nobody writes now, there is no actor to name against `design:371`, no cadence host to find, and no interaction with P5-C35's gate. The r4 reading of `movement:113` is accepted in full — "Live handlers use the shared store CAS service; boot reconciliation alone consumes each journal outcome exactly once in the same CAS and applies its abort/unpark" makes any daemon-side abort a **Live** Abort — and P5 therefore **performs no abort outside `movement:115`'s `requested|parked`**. Inspect on every row is a GET navigation to Health `daemon-machine#deploy:<ref>` [P5-C19]; it mutates nothing, so it never competes with `design:264`'s "exactly the state-valid action".

`[PLAN]` **Why `swapping`/`resuming` offer no Abort, and what happens instead** [P5-C18]. The store's edge map does permit `aborted` from both, but `movement:90` and `movement:113` say only `swapping|resuming` arm the 20-minute hard `swapDeadlineAt` and that **its expiry invokes journal recovery** — the movement §2.5 recovery table (`movement:164,168-174`), driven by the root recovery timer, not by an Inbox control. `movement:113` also states that requested/parked "have no automatic expiry and remain prominently abortable", which is exactly the split above. **W3 asserts the escalation path explicitly**: a `swapping` deployment past `swapDeadlineAt` projects an item whose only control is Inspect, and the projector emits one deduplicated escalation subject naming the deployment ref and the expired deadline — never a silent stall and never an Inbox Abort.

`[SPEC]` Lifecycle is design 266: the item changes action with its canonical Deployment state and vanishes only after terminal Acknowledge. `[PLAN]` **Deploy (green) and Confirm (breaking) are the two entry verbs, and each both writes the record and invokes the helper `deploy` verb in the same handler** [P5-C49]. **Deploy** calls `store.ts#createDeployment` with all seven `CREATE_KEYS` pinned [P5-C36]: `deploymentRef` from the `deploy-ready` subject [P5-C17]; `idempotencyKey = "deploy:<targetSha>"`; `initialState:'requested'`; `targetCommit` = `DeployReadyPort.latestCandidate().sha`; `previousCommit` = the live SHA the activation reader reported in the same projection pass (never a checkout read); `requestedAt` = the request's `ctx.now()`; and `parkWarnAt` = `requestedAt + 90 s`, which satisfies the validator's strictly-ahead requirement (`deploymentState.ts:163-164`) and matches the bounded wait of `movement:90` — then, on the created revision, invokes the helper. **`parkWarnAt` is written exactly as the store writes it today** (`store.ts:3687`) and no P5 code reads it [P5-C62]. **Confirm over `deploy-ready:<sha>` does the same thing Deploy does** [P5-C58]: the identical seven pinned `CREATE_KEYS` at `initialState:'requested'`, then the helper — the only difference is which verb the candidate's `breaking` flag admits, so the breaking record is born at `requested` and never at `waiting-confirmation`. **Confirm over `deployment:<n>` creates nothing**: it is one `store.ts#transitionDeployment` CAS `waiting-confirmation → requested` on the pinned `expectedRevision`/`expectedState` followed by the same helper call, kept so the spec state is handled exhaustively even though P5 has no writer that can produce it. A stale revision is `409` with no helper invocation, and a Deploy or Confirm whose `deploy-ready:<sha>` is no longer the current candidate is `409 revision-changed` with no store write and no helper invocation [P5-C58]. **No P5 code contains a second deployment transition path**: `control/store.ts#transitionDeployment` stays the sole mutator, and §9 probe 3 enforces it.

`[SPEC]` Design 371: a deploy-ready item is projected **only** when tested green `main` is strictly newer than the immutable VM live release. `[PLAN]` **Where "tested green" comes from** [P5-C42]: no module produces a deploy candidate today, so W0 declares the closed port `DeployReadyPort { latestCandidate(): { sha: string; attestationDigest: string; breaking: boolean } | null }` and W1 implements it in `dashboard/server/deploy/deployReady.ts` over the existing attested release tree — the same reader Home uses (`schedules/attestedSource.ts:56-66` via `home/routes.ts:25-42`) plus the candidate release's `MANIFEST.sha256` and `VERSION`. **Tested-green is defined as "a release exists at `/opt/kb-releases/<sha>` with verified attestation sidecars"**, which is the only green signal the VM has: CI gates `main` before any release is built, so an unbuilt commit is simply not a candidate. `attestationDigest` is that release's verified archive digest — the same value the T3 preimage pins (§3.3) and the helper `deploy` request carries (§3.4). `breaking` is the presence of a `BREAKING` marker file in the release tree, emitted by `scripts/build_platform_release.py` from a `BREAKING` file at the source root; **W1 owns that packer change and its `tests/test_build_platform_release.py` case**. The store's single-active refusal (`store.ts:3676-3678`) covers only the non-terminal half; the unacknowledged half is the projector's. Any unmet condition yields no item, never a disabled one. **Green and breaking share one projection and differ only in the verb offered** [P5-C58]. Both emit the derived `deploy-ready:<sha>` subject; `breaking:false` offers Deploy and `breaking:true` offers Confirm, and in both cases **no Deployment record exists until the operator acts**. `deployReady.ts` is therefore a **pure reader with no timer, no cadence host, and no write path of any kind** — `latestCandidate()` is called on the projection read, the whole feature contains no dashboard-initiated store mutation, and `GET /api/inbox` writes nothing, which is what `design:367` ("Inbox remains a projection and is never directly mutated") requires and what the r4 review found the 60-second poll could not satisfy against `design:363,534`. Candidate turnover needs no mechanism: when a newer attested release lands, `latestCandidate()` returns the new sha, the old subject stops being projected, and the idempotency of `createDeployment` (`idempotencyKey = "deploy:<targetSha>"` against the store's conflict refusal at `store.ts:3672`) still makes a double-clicked Deploy or Confirm converge on one record. **No Deployment field is added**, so `DEPLOYMENT_KEYS`/`STORED_DEPLOYMENT_KEYS`/`PATCH_FIELDS` and the `hasExactKeys` decode at `deploymentState.ts:206` are untouched and every pre-P5 stored document still reads [P5-C34, P5-C62].

### 3.2 Asset-pull intent record and Inbox item

`[SPEC]` movement 256 fixes the record verbatim: `AssetPullIntent = {intentRef,runRef,manifestDigest,state,requestedAt,attempts,result}`, created only for a succeeded run with a stored manifest digest, and the endpoint never pretends the VM performed the desktop transfer. Design 257 fixes the Inbox subject `{intentRef,runRef,manifestDigest}` and design 266 fixes the lifecycle: a successful pull vanishes on the helper receipt; offline or failure stays visible and retryable.

`[PLAN]` `state` is the closed union `'pending' | 'in-flight' | 'succeeded' | 'failed' | 'offline'`. `manifestDigest` is 64 lowercase hex; `intentRef` is `assetpull-<32 hex>`; `attempts` is a non-negative integer capped at 32; `result` is `null | {outcome:'succeeded'|'failed'; receiptAt; errorCode}` with `errorCode` in the closed union `unavailable|timeout|digest-mismatch|refused|invalid`. The record joins the control-plane document beside `deployments` under the same exact-key discipline (`deploymentState.ts:44-57` is the pattern) and commits at durability `'ordinary'`, not `'deploy-critical'` — an asset pull is not a release transition. Action mapping is total: `pending` ⇒ **Pull home**; `in-flight` ⇒ **Inspect**; `failed`/`offline` ⇒ **Retry**; `succeeded` ⇒ item absent. `id = sha256("asset-pull" + "\0" + intentRef)`. Pull and Retry reuse one idempotency key `pull-assets:<intentRef>:<manifestDigest>` so the resident retry loop of movement 256 resends the same key until the helper reports success or failure.

### 3.3 T3 token binding and refusal

`[SPEC]` design 528: a T3 gate or deploy kind requires a WebAuthn assertion pinned to subject, revision, decision, and digest; a missing ceremony refuses and never downgrades. Design 670: tailnet-only deployments return `403 ceremony-unavailable` and no lower channel exists.

`[PLAN]` **P5 writes no new T3 verifier. It extends the shipped one in place** [P5-C20, `design:500`]. `control/humanResponse.ts` and the challenge endpoint at `control/routes.ts:1831-1855` gain a **`deploy` purpose** whose binding tuple is `{deploymentRef, targetCommit, action}`, minted through the same `credentialStore.ts` single-use pending map and verified through the same `T3_KINDS`/`riskTier`/`responseDigest` path. Concretely, W2 adds `deployChallenge(input)` beside `humanResponseChallenge` (`humanResponse.ts:80`) and `deployDigest(input)` beside `humanResponseDigest` (`:72`); W6.3 registers `POST /api/inbox/deployment/:ref/challenge` next to the existing endpoint on the same guarded scope. Nothing named `auth/deployCeremony.ts`, `deploy/t3Token.ts`, or a second refusal ladder is created.

The challenge preimage is the canonical UTF-8 encoding of `kb.deploy-t3/v1\0<subject>\0<ref>\0<revision>\0<decision>\0<digest>`, where `subject ∈ {'deployment','pty-quiescence'}`, `ref` is the `deploymentRef`, `revision` is the pinned `deployment:<n>` string [P5-C28] except on `deploy` and on the candidate arm of `confirm`, where it is the derived `deploy-ready:<sha256>` revision — **the same closed two-spelling union the `confirm` endpoint parses** [P5-C58] — `decision ∈ {'deploy','confirm','abort','close-ptys-and-continue'}` — **the four T3 verbs, Confirm included because `movement:254` makes it the breaking deploy's entry verb** [P5-C47, P5-C49] — and `digest` is `DeployReadyPort.latestCandidate().attestationDigest`, re-read server-side, for `deploy` and for `confirm` over a `deploy-ready:<sha>` [P5-C42] (a ref sha that is no longer the current candidate is refused `409 revision-changed` **before** any ceremony work, so a stale candidate can never be signed), the attestation digest the release tree reports for the record's own `targetCommit`, re-read server-side, for `confirm` over a `deployment:<n>`, the stored `Deployment.targetCommit`'s recorded attestation digest for `abort`, or `sha256(sorted blockingPtyIds joined by "\0")` for `close-ptys-and-continue`. Verification recomputes the preimage server-side from the store record and compares bytes; it never accepts a client-supplied preimage. A grant is single-use, consumed under the same store CAS as the transition, and expires in 120 seconds — deliberately narrower than the endpoint's own five-minute challenge window (`control/routes.ts:1854`) and wider than the 5-second execution-unlock window (`activation.ts:194-200`), because a deploy ceremony precedes a bounded network call rather than an in-process wiring construction. **No grant ever spans a human wait** [P5-C49, P5-C58]: the breaking path's assertion is minted and consumed inside the single Confirm request that creates the record and calls the helper, so the unbounded wait sits entirely **before** the ceremony — there is no earlier materialisation whose authority could be carried forward, and the helper is never reached on a session cookie alone.

`[PLAN]` **The refusal ladder is the shipped one, unchanged and never extended.** No ceremony port, or no credential provisioned through `DASHBOARD_WEBAUTHN_CREDENTIALS` [P5-C45] ⇒ **`403 ceremony-unavailable`** (`humanResponse.ts:144`; `routes.ts:1835,1851`). Missing, unparseable, unverifiable, wrong-origin, or **digest/revision-mismatched** assertion ⇒ **`403 ceremony-invalid`** (`:145,148,162,164`) — there is no `ceremony-mismatch` code and P5 does not mint one. Expired challenge ⇒ `403 ceremony-expired` (`:149`). A replayed assertion ⇒ `409` under the store CAS. Session authentication alone never satisfies a T3 endpoint, and the browser disables the control while also proving the server refuses it (`design:617`). Error bodies carry a fixed code and no key, signer, challenge, or credential material.

`[PLAN]` **Reachability on the VM** [P5-C23]. `control/routes.ts:1834` today refuses the challenge unless `ctx.authMode === 'win32-desktop' && ctx.credentials().length !== 0`, which makes T3 unreachable on the tailnet Linux VM. P5 replaces that clause with **"auth mode `tailnet` or `win32-desktop`, with ≥1 provisioned WebAuthn credential for the operator"**, written as an exhaustive `switch` over `AuthMode` (`auth/mode.ts:24`, the closed union `'win32-desktop' | 'tailnet'`) whose `default` arm is a `never` assertion, so a future third mode fails to compile instead of being auto-admitted [P5-C45]. **The credential source is pinned**: `ctx.credentials()` resolves only from `DASHBOARD_WEBAUTHN_CREDENTIALS` (`auth/credentialStore.ts:41-45#resolveCredentials`), and `/api/auth/register/verify` merely *reports* material for a human to provision (`auth/routes.ts:194-196`) and grants nothing — **no runtime registration path can create a credential**, so "provisioned" means operator-provisioned out of band and is not attacker-reachable. With zero provisioned credentials the endpoint still answers `403 ceremony-unavailable`: the gate loosens on auth mode and never on credential possession, and no path downgrades to session-only authority. After the lift, any authenticated tailnet session can *mint* deploy challenges — an oracle/DoS surface, not an authz change, since verification still needs the provisioned key — and it is bounded by the existing mutation rate guard on that scope, which P5 does not alter. The tests are named in §5 W6.3.

### 3.4 Desktop-helper client and closed payload/result union

`[SPEC]` movement 235 fixes the **request** union exactly — `deploy {sourceCommit,attestationDigest,requestRef}`, `pull-assets {intentRef,runRef,manifestDigest}`, `deployment-result {deploymentRef,outcome}` — with one deploy request plus a five-minute cooldown, independently idempotent and rate-limited pull/result, and no verb accepting paths, hosts, commands, or keys. movement 237 fixes the **receipt**: before signing, every accepted or refused invocation appends and fsyncs one canonical JSONL record to `%LOCALAPPDATA%\kb\deploy-helper\invocations.jsonl` with time, request ref, short SHA, caller node, and outcome — never secrets or signatures. Design 527 forbids returning signer or key material.

`[PLAN]` **The RESULT is the movement §3 receipt record, verbatim — a plan requirement, not a spec fact** [P5-C46, P5-C52]. `[SPEC]` fixes only the *fields*: `movement:235` the request union, and `movement:237` the canonical JSONL receipt that every accepted or refused invocation appends and fsyncs before signing, carrying time, request ref, short SHA, caller node, and outcome and never secrets or signatures. `movement:237` describes a **local log file** and defines no wire response, so `[PLAN]` **P5 REQUIRES the helper to reply to the dashboard with that record verbatim**, which keeps `design:613`'s "payload/result remain the movement §3 closed union" literally true and needs no spec amendment (§12). **Ownership of the two sides is split** [P5-C52]: the helper-side obligation to emit that reply belongs to the **movement helper build and is out of P5's scope** (§11), carried as a P7 item; the dashboard-side decoder that enforces it is W2's. The r2 plan's invented `[PLAN]` result union and its twelve-code `refusalCode` vocabulary are **deleted**.

`[PLAN]` `dashboard/server/deploy/helperClient.ts` is the only module in `dashboard/server` permitted to speak the helper protocol. It encodes exactly the three verbs, rejects any extra or unknown field before serialization, and decodes the receipt record against the exact-key wall of `protocol.schema.json`. From that record — and from nothing else — it derives its **closed internal `HelperOutcome`** (plan-owned, W2): `{verb; requestRef; receiptAt; shortSha; callerNode; outcome:'accepted'|'refused'|'failed'}`, a projection of receipt fields that invents no vocabulary.
