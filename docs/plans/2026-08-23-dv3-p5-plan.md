## 3. Domain/contract deltas

`[SPEC]` is fixed by the cited design or movement spec. `[PLAN]` closes a choice the specs leave open. W0 makes every type and vector below compile before any behavior work.

### 3.1 Deployment Inbox item and action union

`[SPEC]` The item shape is design 256 verbatim: `{kind:'deployment'; subject:{deploymentRef}; title; state; blockingPtyIds: string[]}` over the `InboxBase` of `design:249-253`, whose `revision` is a **string** (`design:252`). `[PLAN]` `state` is the closed union `DEPLOYMENT_STATES` (`deploymentState.ts:12-22`) plus `'deploy-ready'` [P5-C17]; `deploymentRef` is either a stored `Deployment.deploymentRef` or the derived `deploy-ready:<40 lowercase hex>`, and **the Deployment created from a deploy-ready subject reuses that subject's `deploymentRef` verbatim**, so the id is stable across Deploy [P5-C17]. `id = sha256("deployment" + "\0" + deploymentRef)`, matching `p4-plan:194`'s ID rule.

`[PLAN]` **The `revision` stringify/parse rule** [P5-C28]. `Deployment.revision` is a number; the Inbox item carries the string `deployment:<n>` with `n` the decimal store revision, no padding and no leading zero. All six action endpoints parse `expectedRevision` back with the closed parser `/^deployment:(0|[1-9][0-9]{0,15})$/` and refuse anything else — a bare number, a padded number, a foreign prefix, or a value out of range — with `400 invalid-revision` **before** any store read, ceremony verification, or helper call. A deploy-ready subject carries `revision = "deploy-ready:" + sha256(targetSha + "\0" + liveSha)`, which the same parser refuses on every endpoint except `deploy`.

`[PLAN]` `blockingPtyIds` is the sorted unique set of live PTY session ids from the P3 registry snapshot, each matching `/^pty-[0-9a-f]{32}$/`. **It is the live set at projection time in any pre-swap state, not only `parked`**: `design:264` pins the exact live session ids and never restricts which state may carry them, so the r1 narrowing ("empty for every non-`parked` state") is dropped [P5-C39].

`[PLAN]` The action is the total single-valued function of P5-C18 — **one MUTATING control per item; Inspect is navigation and is always present alongside it**:

| Condition (evaluated in order) | Mutating action | T3 | Endpoint |
|---|---|---|---|
| `blockingPtyIds.length > 0` | Close PTYs and continue | yes | `POST /api/inbox/deployment/:ref/close-ptys-and-continue` |
| `state === 'waiting-confirmation'` | Confirm, **or Abort to decline** | yes [P5-C21] | `POST …/confirm`, `POST …/abort` |
| `state === 'deploy-ready'` | Deploy | yes | `POST /api/inbox/deployment/:ref/deploy` |
| `state ∈ {requested,parked}` and `abortRequestedAt === null` | Abort | yes | `POST /api/inbox/deployment/:ref/abort` |
| `state ∈ {requested,parked}` with an abort already requested | — none (Inspect only) | — | — |
| `state ∈ {swapping,resuming}` | — **none; Abort is NOT offered** | — | — |
| `state ∈ {succeeded,aborted,failed}` | Acknowledge | no [P5-C21] | `POST /api/inbox/deployment/:ref/acknowledge` |
| `state === 'acknowledged'` | — item absent | — | — |

Inspect on every row is a GET navigation to Health `daemon-machine#deploy:<ref>` [P5-C19]; it mutates nothing, so it does not compete with `design:264`'s "exactly the state-valid action".

`[PLAN]` **Why `swapping`/`resuming` offer no Abort, and what happens instead** [P5-C18]. The store's edge map does permit `aborted` from both, but `movement:90` and `movement:113` say only `swapping|resuming` arm the 20-minute hard `swapDeadlineAt` and that **its expiry invokes journal recovery** — the movement §2.5 recovery table (`movement:164,168-174`), driven by the root recovery timer, not by an Inbox control. `movement:113` also states that requested/parked "have no automatic expiry and remain prominently abortable", which is exactly the split above. **W3 asserts the escalation path explicitly**: a `swapping` deployment past `swapDeadlineAt` projects an item whose only control is Inspect, and the projector emits one deduplicated escalation subject naming the deployment ref and the expired deadline — never a silent stall and never an Inbox Abort.

`[SPEC]` Lifecycle is design 266: the item changes action with its canonical Deployment state and vanishes only after terminal Acknowledge. `[PLAN]` Deploy and Confirm on a `deploy-ready` subject call `store.ts#createDeployment` with all seven `CREATE_KEYS` pinned [P5-C36]: `deploymentRef` from the subject [P5-C17]; `idempotencyKey = "deploy:<targetSha>"`; `initialState` per P5-C17; `targetCommit` = the tested-green head; `previousCommit` = the live SHA the activation reader reported in the same projection pass (never a checkout read); `requestedAt` = the request's `ctx.now()`; and `parkWarnAt` = `requestedAt + 90 s`, the settled bounded wait of `movement:90`. Every other action calls `store.ts#transitionDeployment` with the pinned `expectedRevision` and `expectedState` the item carried. A stale revision is `409` with no helper invocation. **No P5 code contains a second deployment transition path**: `control/store.ts#transitionDeployment` stays the sole mutator, and §9 probe 3 enforces it.

`[SPEC]` Design 371: a deploy-ready item is projected **only** when tested green `main` is strictly newer than the immutable VM live release. `[PLAN]` The projector requires all of: the release reader reports an available live SHA; `main`'s tested-green head is a strict descendant of it; and **there is no Deployment that is either non-terminal OR terminal-but-unacknowledged** [P5-C35] — a `succeeded`/`aborted`/`failed` record whose `acknowledgedBy` is still null keeps its own Acknowledge item, so admitting a deploy-ready subject beside it would put two deployment subjects in Inbox at once. The store's single-active refusal (`store.ts:3676-3678`) covers only the non-terminal half; the unacknowledged half is the projector's. Any unmet condition yields no item, never a disabled one.

### 3.2 Asset-pull intent record and Inbox item

`[SPEC]` movement 256 fixes the record verbatim: `AssetPullIntent = {intentRef,runRef,manifestDigest,state,requestedAt,attempts,result}`, created only for a succeeded run with a stored manifest digest, and the endpoint never pretends the VM performed the desktop transfer. Design 257 fixes the Inbox subject `{intentRef,runRef,manifestDigest}` and design 266 fixes the lifecycle: a successful pull vanishes on the helper receipt; offline or failure stays visible and retryable.

`[PLAN]` `state` is the closed union `'pending' | 'in-flight' | 'succeeded' | 'failed' | 'offline'`. `manifestDigest` is 64 lowercase hex; `intentRef` is `assetpull-<32 hex>`; `attempts` is a non-negative integer capped at 32; `result` is `null | {outcome:'succeeded'|'failed'; receiptAt; errorCode}` with `errorCode` in the closed union `unavailable|timeout|digest-mismatch|refused|invalid`. The record joins the control-plane document beside `deployments` under the same exact-key discipline (`deploymentState.ts:44-57` is the pattern) and commits at durability `'ordinary'`, not `'deploy-critical'` — an asset pull is not a release transition. Action mapping is total: `pending` ⇒ **Pull home**; `in-flight` ⇒ **Inspect**; `failed`/`offline` ⇒ **Retry**; `succeeded` ⇒ item absent. `id = sha256("asset-pull" + "\0" + intentRef)`. Pull and Retry reuse one idempotency key `pull-assets:<intentRef>:<manifestDigest>` so the resident retry loop of movement 256 resends the same key until the helper reports success or failure.

### 3.3 T3 token binding and refusal

`[SPEC]` design 528: a T3 gate or deploy kind requires a WebAuthn assertion pinned to subject, revision, decision, and digest; a missing ceremony refuses and never downgrades. Design 670: tailnet-only deployments return `403 ceremony-unavailable` and no lower channel exists.

`[PLAN]` **P5 writes no new T3 verifier. It extends the shipped one in place** [P5-C20, `design:500`]. `control/humanResponse.ts` and the challenge endpoint at `control/routes.ts:1831-1855` gain a **`deploy` purpose** whose binding tuple is `{deploymentRef, targetCommit, action}`, minted through the same `credentialStore.ts` single-use pending map and verified through the same `T3_KINDS`/`riskTier`/`responseDigest` path. Concretely, W2 adds `deployChallenge(input)` beside `humanResponseChallenge` (`humanResponse.ts:80`) and `deployDigest(input)` beside `humanResponseDigest` (`:72`); W6.3 registers `POST /api/inbox/deployment/:ref/challenge` next to the existing endpoint on the same guarded scope. Nothing named `auth/deployCeremony.ts`, `deploy/t3Token.ts`, or a second refusal ladder is created.

The challenge preimage is the canonical UTF-8 encoding of `kb.deploy-t3/v1\0<subject>\0<ref>\0<revision>\0<decision>\0<digest>`, where `subject ∈ {'deployment','pty-quiescence'}`, `ref` is the `deploymentRef`, `revision` is the pinned `deployment:<n>` string [P5-C28], `decision ∈ {'confirm','deploy','abort','close-ptys-and-continue'}`, and `digest` is the target commit's attestation digest for `deploy`/`confirm`, or `sha256(sorted blockingPtyIds joined by "\0")` for `close-ptys-and-continue`. Verification recomputes the preimage server-side from the store record and compares bytes; it never accepts a client-supplied preimage. A grant is single-use, consumed under the same store CAS as the transition, and expires in 120 seconds — deliberately narrower than the endpoint's own five-minute challenge window (`control/routes.ts:1854`) and wider than the 5-second execution-unlock window (`activation.ts:194-200`), because a deploy ceremony precedes a bounded network call rather than an in-process wiring construction.

`[PLAN]` **The refusal ladder is the shipped one, unchanged and never extended.** No ceremony port, or no registered credential for the operator ⇒ **`403 ceremony-unavailable`** (`humanResponse.ts:144`; `routes.ts:1835,1851`). Missing, unparseable, unverifiable, wrong-origin, or **digest/revision-mismatched** assertion ⇒ **`403 ceremony-invalid`** (`:145,148,162,164`) — there is no `ceremony-mismatch` code and P5 does not mint one. Expired challenge ⇒ `403 ceremony-expired` (`:149`). A replayed assertion ⇒ `409` under the store CAS. Session authentication alone never satisfies a T3 endpoint, and the browser disables the control while also proving the server refuses it (`design:617`). Error bodies carry a fixed code and no key, signer, challenge, or credential material.

`[PLAN]` **Reachability on the VM** [P5-C23]. `control/routes.ts:1834` today refuses the challenge unless `ctx.authMode === 'win32-desktop' && ctx.credentials().length !== 0`, which makes T3 unreachable on the tailnet Linux VM. P5 replaces that clause with **"≥1 REGISTERED WebAuthn credential for the operator, in any auth mode"** — `ctx.credentials().length !== 0` alone. With zero registered credentials the endpoint still answers `403 ceremony-unavailable`, so the gate loosens on auth mode and never on credential possession, and no path downgrades to session-only authority. The tests are named in §5 W6.3.

### 3.4 Desktop-helper client and closed payload/result union

`[SPEC]` movement 235 fixes the **request** union exactly — `deploy {sourceCommit,attestationDigest,requestRef}`, `pull-assets {intentRef,runRef,manifestDigest}`, `deployment-result {deploymentRef,outcome}` — with one deploy request plus a five-minute cooldown, independently idempotent and rate-limited pull/result, and no verb accepting paths, hosts, commands, or keys. movement 237 fixes the **receipt**: before signing, every accepted or refused invocation appends and fsyncs one canonical JSONL record to `%LOCALAPPDATA%\kb\deploy-helper\invocations.jsonl` with time, request ref, short SHA, caller node, and outcome — never secrets or signatures. Design 527 forbids returning signer or key material.

`[PLAN]` **The wire RESULT union is a plan invention, not spec** [P5-C26]. movement §3 defines the request union and the JSONL receipt and **nothing else** — there is no wire result shape and no `refusalCode` vocabulary anywhere in the movement or design specs. P5 therefore declares the result union itself, under two rules: **the fsynced JSONL receipt (movement 237) is the only durable truth**, and the wire result is a derived convenience the client re-validates against the receipt before any store write. **No spec amendment is proposed** (§12), because P5 adds a client-side contract, not a helper-side one.

`[PLAN]` `dashboard/server/deploy/helperClient.ts` is the only module in `dashboard/server` permitted to speak the helper protocol. It encodes exactly the three verbs, rejects any extra or unknown field before serialization, and decodes only the closed `[PLAN]` result union `{verb; requestRef; outcome:'accepted'|'refused'|'failed'; refusalCode?; receiptAt}` with `refusalCode` in `forged-node|forged-source|forged-attestation|unknown-verb|unknown-field|repeat-key|cooldown|stale-revision|active-pty|failed-swap|rollback|misleading-symlink`. Every response is validated by an exact-key wall; an unknown key, an unknown verb echo, or any field resembling a signature, key, or path fails closed as `refused` with `errorCode:'invalid'` and never reaches the store. Transport is a bounded HTTPS call to the pinned desktop tailnet address with a 20-second timeout and no redirects; the VM never learns a helper filesystem path.

`[PLAN]` **Prerequisite schema check (design 667)** [P5-C27]. There is no descriptor to generate from movement §3 — it is prose — so P5 owns one: **`dashboard/server/deploy/helper/protocol.schema.json`, a plan-authored JSON Schema written by W2**, enumerating the three request verbs with their exact movement 235 fields and the receipt fields of movement 237. The client validates **both directions** against it: every outbound request before serialization, and every inbound receipt (and the result derived from it) before decoding. Before the first Deploy of a daemon lifetime the client fetches the helper's advertised protocol version and compares it against the schema's `$id` version; **a mismatch or an unfetchable advertisement fails closed** — Deploy is not offered, no request is sent, and one deduplicated escalation card is created through the P4 reconciliation publisher. **The helper itself is NOT rewritten** (`design:611`); only its messages are validated. Pull home is likewise offered only after the helper advertises `pull-assets/v1` (movement 256).

The whole `daemon-machine` composition is additionally wrapped at 2500 ms. Raw `stderr` never reaches a row; spend fields are omitted, never zeroed.

### 3.6 Home version source

### 3.7 Quiescence and close-ptys-and-continue

`[SPEC]` design 264: close-and-continue is part of deploy quiescence, pins the exact live session ids and deployment revision, records Daniel as actor, and refuses unless every `closeAndWait` confirms. Design 619 and 673: deploy closes exact live ids only through Daniel's quiescence action.

`[PLAN]` The action takes `{deploymentRef, expectedRevision, sessionIds}` plus the T3 assertion whose digest pins `sha256(sorted sessionIds)`. The server re-reads the live session set and refuses `409 pty-set-changed` if it differs by even one id — it never closes a superset, a subset, or a re-derived set. It then calls the P3 `DeploymentSessionCloser` (`pty/sessionRecord.ts:129`) with exactly those ids. **Any non-`ok` result, including one `closeAndWait` timeout, refuses the whole action** with `409 pty-not-confirmed`, leaves the Deployment revision untouched, and re-projects the item with the still-blocking ids. Only an `ok` result with `closed` equal to the pinned set advances `parked → swapping`, recording `actor:'human-operator'` with Daniel's attribution (`auth/operator.ts:18,64`).

Each probe's assertion: **forged-node** — a caller whose Tailscale-derived node identity is not the pinned VM is refused before any signer call. **forged-source** — a `sourceCommit` that is not a strict descendant of the live SHA is refused and no request is sent. **forged-attestation** — an `attestationDigest` disagreeing with the archive digest is refused; no partial activation occurs. **unknown-verb** — a verb outside the movement 235 union fails closed with no store write and no request sent. **unknown-field** — an extra request field and an extra result key each fail the `protocol.schema.json` wall closed with no store write [P5-C27]. **repeat-key** — the same idempotency key returns the original receipt and opens no second request. **cooldown** — a second deploy inside five minutes is refused with `cooldown` and no request leaves the VM. **stale-revision** — a transition pinned to an outdated Deployment revision is `409` with no helper invocation. **active-pty** — a deployment with live PTYs offers only `close-ptys-and-continue`, and a `closeAndWait` timeout refuses `409 pty-not-confirmed` while leaving the revision untouched. **failed-swap** — an injected swap failure lands in `failed` with the error retained and only Acknowledge offered. **rollback** — a rollback is a deliberate movement §2.5 transition and is never reachable as an Inbox Abort. **misleading-symlink** — a `current` symlink pointing outside `/opt/kb-releases` is refused by the release reader, which reports unavailable rather than a wrong SHA.
