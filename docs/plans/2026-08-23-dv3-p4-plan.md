### 3.1 Learning proposal record

`[SPEC]` One UTF-8 Markdown file under `docs/proposals/learnings/` is one record, named `<created-date>-<id>.md`; its complete body is (`design:318-337`):

```text
schema: kb.learning-proposal/v1
id: lessons-miner-run_01HXYZ-01
kind: lesson | agent-improvement | grade-finding | model-audit | hygiene | context-lifecycle
source-agent: lessons-miner
source-run: run_01HXYZ
created-at: 2026-08-20T05:30:00Z
target: agents/fyt-checker.md
status: proposed | implemented
batch-id: null
implemented-at: null
---
## Evidence
- path: memory/lessons-miner.md
  locator: "2026-08-20 run_01HXYZ"
## Proposed change
One bounded, testable change.
```

`[PLAN]` `source-agent` matches `[a-z0-9]+(?:-[a-z0-9]+)*` (1-64 bytes), `source-run` matches `run[-_][A-Za-z0-9][A-Za-z0-9._-]{0,94}` (accepting the design example and current `run-<uuid>` refs), and `created-at` is a canonical UTC second supplied by the server schedule receipt. `ordinal` is 1-based after candidates are sorted by `(kind,target,sha256(canonical proposed-change),sha256(canonical evidence rows))`; `id = <source-agent>-<source-run>-<ordinal as two digits>`. The filename date is the first ten bytes of `created-at`. Re-running the same source run must render byte-identical paths/bodies. Duplicate IDs with changed bodies fail closed.

`[SPEC]` `target` is exactly one normalized repository-relative path and the Evidence block is inert. `[PLAN]` parsing is closed: exactly the listed frontmatter keys in that order, one delimiter, one Evidence block containing 1-20 `{path,locator}` rows, and one non-empty Proposed-change block of at most 8 KiB. Unknown/duplicate keys, CR/NUL/control bytes, YAML aliases/tags, absolute/drive/UNC/dot paths, or symlink paths reject structurally. Imperative text inside a valid Evidence path/locator remains inert string data and is never copied to a worker prompt or command. Parser output contains strings only; it has no execution callback.

`scripts/learning_proposals.py` is the sole Markdown parser/renderer. Server code executes it for closed JSON output and decodes that DTO with W0 contracts; it does not implement a second Markdown parser or read the Python source.

### 3.2 Implementer and durable path manifest

`[SPEC]` Implementer consumes only `status: proposed`, at most five records, with non-conflicting targets; a worker edits in a worktree and never commits/merges. One PR contains target edits and the same proposal records changed only to `status: implemented`, common `batch-id`, and common `implemented-at` (`design:338-346,665`).

`[PLAN]` The target wall first delegates to `scripts.agent_maintainer.validate_target_path`, then requires `classifyTarget(target) === 'durable'`. The exact Implementer set is therefore one existing `agents/<name>.md` or `routines/roles/<name>.md`, with no additional subdirectory, executable source, symlink/reparse point, or case-fold duplicate; `memory/<name>.md` remains legal agent-maintainer evidence but is coordination and cannot enter a durable PR. All records are parsed before worktree creation. A batch sorts by target then ID; duplicate targets or a target equal to any proposal-record path reject the whole batch. `batch-id = learn-<first 24 hex of sha256(baseCommit + "\0" + sorted record ids)>`; `implemented-at` is one server UTC second. The worker receives only Proposed-change text plus the target's bytes; Evidence is excluded from its prompt. After the worker returns, the server rejects changed paths outside the exact target set and renders record-state changes itself.

The TS wall invokes a fixed Python module entry through the injected bounded process runner, sends `{repoRoot,target}` on JSON stdin, and accepts only the normalized JSON stdout; target text is never interpolated into Python source or a shell command. The argv is `py -3 -c <fixed module entry>` on Windows and `python3 -c <same entry>` on Linux, `shell:false`, 15-second timeout, 1 MiB stdout/64 KiB stderr caps. It then performs the durable-classifier/existence checks in TS. This reuses the Python wall by execution rather than copying or loading it.

`[PLAN]` replace—not overload—`routeDurable(repoRoot, relpath, ...)` with `routeDurable(repoRoot, manifest, ...)`, updating both existing callers. The manifest is:

```text
schema: kb.durable-path-manifest/v1
operationKey: <kind-scoped idempotency key>
purpose: governed-save | workflow-amendment | learning-proposal | learning-implementation | schedule-mirror
baseCommit: <40 lowercase hex>
relpaths: <sorted unique list, 1..32>
```

New-purpose keys are `learning-proposal:<source-agent>:<source-run>`, `learning-implementation:<batch-id>`, and `schedule-mirror:<batch-id>`; existing callers retain their existing request idempotency key, prefixed by purpose.

Before staging any byte, resolve every path under the repository and reject absolute/drive/UNC/dot/control paths, path length over 240 UTF-8 bytes, symlink/reparse traversal, case-fold duplicates, an unclean pre-existing index, wrong `baseCommit`, or a purpose/path mismatch. Purpose rules are exact: proposal records only under `docs/proposals/learnings/`; implementation is 1-5 such records plus their 1-5 validated targets; schedule mirror is only `HEARTBEAT.md` or `orgs/<slug>/HEARTBEAT.md`; existing governed-save/workflow paths retain their current classifier wall. After `git add -- <all paths>`, the cached path set must equal `relpaths` exactly. Validation/stage failure creates no commit; later failure records `{committed,pushed,prKnown,branch,tip}` and never retries a subset. A timed-out PR open first queries the operation-key branch and accepts exactly one matching PR; ambiguity fails and escalates without deletion. Exact `operationKey` replay returns the original receipt; changed canonical manifest/body under the key is 409. `AsyncPrResult` becomes required pinned `{owner,repo,number,url}`; malformed `gh` output is failure.

For the three new purposes, `durableManifestService` derives—not accepts—head `dv3-p4/<purpose>-<first 16 hex of sha256(operationKey)>`, prepares a dedicated worktree at `baseCommit`, and gives the worker/renderer no git capability; only `routeDurable` commits and pushes. Production base is the attested protected-main commit, supervised tests substitute fixture `main`, and existing governed-save/workflow callers retain their explicitly configured work branch. Worktree preparation is a caller/service concern, not another publisher.

### 3.3 Inbox item and source lifecycle

`[SPEC]` P4 `/api/inbox` contains only PR and escalation subjects (`design:244-273,597`). Deployment/asset items are P5. Runs and STOP are resolvers that create/link escalation cards, never Inbox subjects. No next-fire or run gates.

`[PLAN]` the closed response is `{items: InboxItem[],revision,sources:{pr:SourceState,escalation:SourceState}}`, where:

```text
PrSubject         = {kind:'pr',id,createdAt,revision,subject:{owner,repo,number},title,href}
EscalationSubject = {kind:'escalation',id,createdAt,revision,subject:{cardId},related:{runRef?,stopEvent?},title,reason}
SourceState       = {status:'verified',revision,verifiedAt} | {status:'failed',revision?,verifiedAt?,errorCode,stale}
```

Top-level `revision` is `sha256(canonical sorted source states + sorted item id/revision pairs)`. Error codes are the closed union `unavailable|timeout|overflow|invalid`; browser error text is fixed copy, never raw stderr. `GET /api/inbox?refresh=pr|escalation` refreshes only the named failed source; absent `refresh` reads/reconciles normally and an unknown value is 400, so Retry needs no mutation endpoint.

IDs are `sha256(kind + "\0" + canonicalSubjectKey)`: PR key is lowercase owner/repo plus decimal number; escalation key is normalized card path. PR href is rebuilt from the pinned owner/repo/number, never accepted from subject text. Items sort by `createdAt desc`, then `kind`, then `id`. The PR resolver pins the configured repository, executes a 15-second `gh pr list --state open --limit 101` read, rejects more than 100 or malformed rows as source failure, polls every 60 seconds, and invalidates immediately on a publisher receipt (the §11 line 666 cache/timeout requirement). Resolver snapshots persist through an injected control-store cache port and also invalidate on card store events, run terminal events, and Plane-A STOP changes. On source failure, last-good items remain with `stale:true`; with no last-good data, the explicit failed source row prevents a false empty state. “Nothing needs you” is legal only when both sources are freshly verified and empty.

`[PLAN]` PR merge/close removes only that PR subject; card completion removes only that escalation. Run failure and STOP derive stable source keys `run:<runRef>` and `stop:<sha256(STOP bytes)>`; they lookup completed as well as open cards before requesting an escalation, so resolution cannot recreate one. Escalation card IDs derive from source `createdAt` plus the source-key hash. A card may link one run and/or STOP; those links never become separate items.

### 3.4 Reconciliation intent, CAS, and audit

`[SPEC]` Sweeper is read-only and may emit only `card-transition`, `escalation-card`, `schedule-mirror`, or `mirror-merged` intents. Exactly one server-owned `publishReconciliationIntent` applies card/Inbox transitions and schedule effects using the existing ops outbox and durable publisher (`design:348-373`).

`[PLAN]` the closed intent union is:

```text
Base = {schema:'kb.reconciliation-intent/v1',kind,actor,idempotencyKey,expectedSourceRevision,expectedStoreRevision,exactTargets:string[]}
card-transition = Base & {cardId,expectedCardSha256,fromState,toState,section?:'Feedback'|'Result',block?:string}
escalation-card = Base & {source:{kind:'run'|'stop'|'sweeper-failure',ref,createdAt},title,reason,related:{runRef?,stopEvent?}}
schedule-mirror = Base & {batchId,targetWatermark,manifest:DurablePathManifest}
mirror-merged = Base & {batchId,pr:{owner,repo,number,mergeCommit},mergedAt}
```

Actors are `human-operator|system-sweeper|dashboard-supervisor`; only authenticated Task actions may claim the first. Keys are respectively `card-transition:<actor>:<cardId>:<expectedCardSha256>:<toState>:<sha256(block ?? '')>`, `escalation:<source.kind>:<source.ref>`, `schedule-mirror:<batchId>`, and `mirror-merged:<batchId>:<mergeCommit>`. `exactTargets` is sorted/unique and the publisher recomputes it from the kind payload; mismatch rejects.

The publisher canonical-hashes the complete intent and uses a two-phase store receipt. Under CAS it re-reads source bytes/revisions and persists `{idempotencyKey,requestSha256,phase:'prepared',expected revisions,exactTargets}` before an effect. It then applies the existing idempotent card mutation/ops outbox or bounded durable publisher and CAS-advances the receipt to `{phase:'published',result,auditRef}`. A replay of `prepared` reconciles the operation key against the ops audit/remote branch before completing; it never blindly repeats. Exact published replay returns the original result; same key/different hash is 409; stale source/store revision is 409 with no bytes staged. Audit records contain actor, intent kind/key/hash, old/new revisions, exact paths, publisher receipt/PR, timestamps, and outcome, but no secrets. Sweeper imports no filesystem-write, git, card mutation, outbox-publish, or credential-bearing capability. A Sweeper execution failure yields one deduplicated `escalation-card` intent from `dashboard-supervisor`; the failed Sweeper does not self-report by writing.

### 3.5 Schedule mirror batch and watermark

`[SPEC]` schedule-store changes mirror to `HEARTBEAT.md` in one batched PR; Sweeper detects drift, `schedule-mirror` publishes, and `mirror-merged` updates `mirroredAt`. Schedule-mirror is write-capable because its publisher creates a PR (`design:357-369`).

`[PLAN]` add store-owned `scheduleMirrorRevision`, incremented only by mirror-relevant create, arm/disarm, delete, and seed reconciliation—not occurrence completion. Each live row/tombstone records `lastMirrorRevision`. A full canonical snapshot of all mirror rows produces `ScheduleMirrorWatermark={revision,digest}`. The renderer is `scripts/schedule_mirror.py`; it is executed for JSON output and never loaded as text. For each distinct `mirrorPath`, it requires exactly one fenced YAML document with one top-level `cadences` sequence, preserves bytes outside that sequence, and renders all live rows assigned to the path sorted by schedule ID with the P2 field order. Missing/duplicate blocks, malformed/duplicate IDs, path escape, more than 32 changed files, or a non-round-tripping render rejects the whole batch.

A batch record is `{schema:'kb.schedule-mirror-batch/v1',id,baseWatermark,targetWatermark,paths:[{path,digest}],state:'prepared'|'pr-open'|'merged'|'failed',operationKey,pr?,createdAt,mergedAt?}` with `id=sha256('schedule-mirror\0'+revision+'\0'+digest)`. At most one batch is open. New mutations while it is open advance the store watermark but never amend the batch/PR; they form the next batch after merge. Exact replay returns the receipt. `mirror-merged` first proves the pinned fixture/real PR is merged and target path digests match, then CAS-updates only rows/tombstones with `lastMirrorRevision <= target.revision`, sets live-row `mirroredAt`, and advances the merged watermark. Changed/stale batches conflict. A byte-identical current watermark is a no-op receipt and opens no PR.
