# Dashboard v3 P4 implementation plan

## 1. Goal + success condition

Implement only design section 10 P4 (`docs/specs/2026-08-20-dashboard-v3-design.md:591-606`). The learning-producing System schedules emit inert, deterministic proposal records; Learnings Implementer may publish a bounded, conflict-free batch through the one durable PR publisher; System Sweeper emits intents but cannot write; the one server-owned reconciliation publisher performs CAS-checked card/Inbox and schedule-mirror effects; and `/api/inbox` projects only pinned PR and escalation subjects.

P4 is complete only when every Verify item at design lines 600-603 has non-skipping evidence: supervised fixtures for every P4 System execution path; proposal parse/ID/target-wall tests; one bounded multi-path PR with records changed to `implemented`; PR/card/run/STOP Inbox lifecycle tests; one read-only Sweeper plus audited replay-safe publisher; schedule full-snapshot batching/watermark races; an isolated bare fixture remote and fixture control store proving publish-review-merge-reconcile without touching the live feature branch or live `main`; Daniel review artifacts; and literal adversarial refusals for all eleven attacks.

Execution is W0, then width-five W1-W5, then serial W6.1-W6.5: 11 tasks. W0 freezes cross-language contracts. Parallel work owns disjoint files and reads only W0 contracts/vectors. Shared registrations, existing callers, UI, agent declarations, `HEARTBEAT.md`, deletion paths, and proof harnesses change only in serial verticals. Each task starts with its named failing test, ends at its literal checkpoint, and does not commit.

### 3.3 Inbox item and source lifecycle

`[SPEC]` P4 `/api/inbox` contains only PR and escalation subjects (`design:244-273,597`). Deployment/asset items are P5. Runs and STOP are resolvers that create/link escalation cards, never Inbox subjects. No next-fire or run gates.

`[PLAN]` the closed response is `{items: InboxItem[],revision,sources:{pr:SourceState,escalation:SourceState}}`, where:

```text
PrSubject         = {kind:'pr',id,createdAt,revision,subject:{owner,repo,number},title,href}
EscalationSubject = {kind:'escalation',id,createdAt,revision,subject:{cardId},related:{runRef?,stopEvent?},title,reason}
SourceState       = {status:'verified',revision,verifiedAt} | {status:'failed',revision?,verifiedAt?,errorCode,stale}
```

Top-level `revision` is `sha256(canonical sorted source states + sorted item id/revision pairs)`. Error codes are the closed union `unavailable|timeout|overflow|invalid`; browser error text is fixed copy, never raw stderr. `GET /api/inbox?refresh=pr|escalation` refreshes only the named failed source; absent `refresh` reads/reconciles normally and an unknown value is 400, so Retry needs no mutation endpoint. `refresh=pr` is rate-limited to **one `gh` subprocess per 30 seconds GLOBALLY** — one server-wide budget, not one per session, so N sessions cannot yield N subprocesses [P4-C34]. The 60-second background poll below draws on the same budget and is the only periodic caller, so nothing spawns `gh` outside it. Inside the window the route spawns nothing and returns the cached projection with `stale: true`. W3 carries the test [P4-C26].

The pinned `<owner>/<repo>` is derived **once at composition** from `git remote get-url origin` of the coordination checkout, through a closed parser that accepts only `github.com[:/]<owner>/<repo>(.git)?` (HTTPS or SSH form) and refuses a missing, ambiguous, non-GitHub, or otherwise unparseable remote by failing composition [P4-C35]. That derivation lives in one new module, `dashboard/server/runtime/repoPin.ts`, **owned by W0**; it is the only new P4 file permitted to spawn `git`, is read-only, and is the fifth named exception in the §3.2 capability table [P4-C40]. That single `{owner,repo}` value feeds `gh pr list --repo`, the server-constructed external PR URL, and the mirror PR; no request, worker, or subject text may supply or override it.

IDs are `sha256(kind + "\0" + canonicalSubjectKey)`: PR key is lowercase owner/repo plus decimal number; escalation key is normalized card path. PR href is rebuilt from the pinned owner/repo/number, never accepted from subject text. Items sort by `createdAt desc`, then `kind`, then `id`. The PR resolver pins the configured repository in the literal command — `gh pr list --repo <owner>/<repo> --state open --limit 101` — and executes it as a 15-second read [P4-C25], rejects more than 100 or malformed rows as source failure, polls every 60 seconds, and invalidates immediately on a publisher receipt (the §11 line 666 cache/timeout requirement). Resolver snapshots persist through an injected control-store cache port and also invalidate on card store events, run terminal events, and Plane-A STOP changes. On source failure, last-good items remain with `stale:true`; with no last-good data, the explicit failed source row prevents a false empty state. “Nothing needs you” is legal only when both sources are freshly verified and empty.

`[PLAN]` PR merge/close removes only that PR subject; card completion removes only that escalation. Run failure and STOP derive stable source keys `run:<runRef>` and `stop:<sha256(STOP bytes)>`; they lookup completed as well as open cards before requesting an escalation, so resolution cannot recreate one. Escalation card IDs derive from source `createdAt` plus the source-key hash. A card may link one run and/or STOP; those links never become separate items.

### 3.4 Reconciliation intent, CAS, and audit

`[SPEC]` Sweeper is read-only and may emit only `card-transition`, `escalation-card`, `schedule-mirror`, or `mirror-merged` intents. Exactly one server-owned `publishReconciliationIntent` applies card/Inbox transitions and schedule effects using the existing ops outbox and durable publisher (`design:348-373`).

`[PLAN]` the closed intent union is:

```text

escalation-card = Base & {source:{kind:'run'|'stop'|'sweeper-failure',ref,createdAt},title,reason,related:{runRef?,stopEvent?}}

```

Actors are `human-operator|system-sweeper|dashboard-supervisor`; only authenticated Task actions may claim the first. Keys are respectively `card-transition:<actor>:<cardId>:<expectedCardSha256>:<toState>:<sha256(block ?? The publisher canonical-hashes the complete intent and uses a two-phase store receipt. That receipt is persisted in `dashboard/server/control/store.ts` and **W6.2 adds it** — the only serial vertical that already owns that file [P4-C33]. W4 writes `reconciliation/publisher.ts` against an injected receipt port backed by an in-memory fake and never edits `store.ts`; W6.2 substitutes the real store implementation and re-runs W4's suites unchanged. Under CAS it re-reads source bytes/revisions and persists `{idempotencyKey,requestSha256,phase:'prepared',expected revisions,exactTargets}` before an effect. It then applies the existing idempotent card mutation/ops outbox or bounded durable publisher and CAS-advances the receipt to `{phase:'published',result,auditRef}`. A replay of `prepared` reconciles the operation key against the ops audit/remote branch before completing; it never blindly repeats. Exact published replay returns the original result; same key/different hash is 409; stale source/store revision is 409 with no bytes staged. Audit records contain actor, intent kind/key/hash, old/new revisions, exact paths, publisher receipt/PR, timestamps, and outcome, but no secrets. Sweeper imports no filesystem-write, git, card mutation, outbox-publish, or credential-bearing capability. A Sweeper execution failure yields one deduplicated `escalation-card` intent from `dashboard-supervisor`; the failed Sweeper does not self-report by writing.

### 3.5 Schedule mirror batch and watermark

`[SPEC]` schedule-store changes mirror to `HEARTBEAT.md` in one batched PR; Sweeper detects drift, `schedule-mirror` publishes, and `mirror-merged` updates `mirroredAt`. Schedule-mirror is write-capable because its publisher creates a PR (`design:357-369`).

`[PLAN]` add store-owned `scheduleMirrorRevision`, incremented only by mirror-relevant create, arm/disarm, delete, and seed reconciliation—not occurrence completion. Each live row/tombstone records `lastMirrorRevision`. Both are **additive fields on the existing versioned control-store document and do NOT bump its version** [P4-C37]: optional on read, defaulted when absent, first written when the first mirror batch is prepared. No migration step and no store rewrite; W5 carries a test that loads a pre-P4 document lacking both fields, reads it without error, and produces a first batch that writes them. A full canonical snapshot of all mirror rows produces `ScheduleMirrorWatermark={revision,digest}`. The renderer is `scripts/schedule_mirror.py`; it is executed for JSON output and never loaded as text. For each distinct `mirrorPath`, it requires exactly one fenced YAML document with one top-level `cadences` sequence, preserves bytes outside that sequence, and renders all live rows assigned to the path sorted by schedule ID with the P2 field order. Missing/duplicate blocks, malformed/duplicate IDs, path escape, more than 32 changed files, or a non-round-tripping render rejects the whole batch.

A batch record is `{schema:'kb.schedule-mirror-batch/v1',id,baseWatermark,targetWatermark,paths:[{path,digest}],state:'prepared'|'pr-open'|'merged'|'failed',operationKey,pr?,createdAt,mergedAt?}` with `id=sha256('schedule-mirror\0'+revision+'\0'+digest)`. At most one batch is open. New mutations while it is open advance the store watermark but never amend the batch/PR; they form the next batch after merge. Exact replay returns the receipt. `mirror-merged` first proves the pinned fixture/real PR is merged and target path digests match, then CAS-updates only rows/tombstones with `lastMirrorRevision <= target.revision`, sets live-row `mirroredAt`, and advances the merged watermark. Changed/stale batches conflict. A byte-identical current watermark is a no-op receipt and opens no PR.
