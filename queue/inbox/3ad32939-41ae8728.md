## Work order

`nextAt` advance is prospective only (fixed in PR #204 for occurrences created going forward, per
finding note F11). Rows whose latest occurrence reached `card-saved` under the pre-fix code keep a
stale, past `nextAt` and report `due=1` on every tick. This is idempotent (no duplicate dispatch)
but noisy, and it means those rows never actually fire on their intended next-day schedule — a
real miss hiding behind harmless-looking log noise.

Write a boot migration/backfill: for every schedule row whose `nextAt` is in the past and whose
latest occurrence already reached `card-saved`, recompute `nextAt` from the cron expression as if
the pre-fix advance had run correctly, then verify the row goes quiet (no longer reports `due=1`)
on the following tick unless genuinely due.

## Acceptance

- A migration/backfill script (or boot-time self-heal) recomputes `nextAt` for every affected row.
- After running it, a tick against the affected rows reports `due=0` unless the row is genuinely
  due by its cron expression.
- The fix is idempotent — running the backfill twice does not change already-correct rows.
