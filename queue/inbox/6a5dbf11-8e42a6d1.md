## Work order

The Wave-A "supervised first Telegram brief send" (brief_notify.py --send, launcher pattern) is
PARKED: the bot token stored in Windows Credential Manager does not authenticate.

What was found (2026-07-20, orchestrator-supervised, token value never read/printed):
- Generic Credential `kb-telegram-bot-token` exists (user `kb-bot`), blob = 96 bytes.
- Decoded exactly the way scripts/desktop_poll.ps1 decodes it (UTF-16), the resulting string does
  not match the Telegram token shape (`digits:35-char-secret`), and the Bot API answers
  HTTP 404 (= invalid token) on getUpdates. A UTF-8 decode does not match the shape either.
- Consequence: the registered-later desktop_poll cadence would ALSO fail silently every cycle
  ("no-credential/404" path) — this blocks the whole Telegram leg, not just the brief send.

To fix (your act — agents never handle the token as an object):
1. Get the bot token from @BotFather (or your records) — format `1234567890:AA...` (~46 chars).
2. Re-store it EXACTLY as the raw string (no quotes, no `bot` prefix, no trailing newline):
   `cmdkey /generic:kb-telegram-bot-token /user:kb-bot /pass:<paste-token>`
   (cmdkey stores UTF-16, which is what desktop_poll.ps1 decodes.)
3. Send any message to the bot from your own Telegram account once (so getUpdates can see your
   chat id — nothing has ever messaged it as far as the API shows).
4. Say the word and the next session runs the supervised send end-to-end
   (`brief_notify.py --send` from the ops worktree via the launcher pattern).
