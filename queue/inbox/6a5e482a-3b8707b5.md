## Work order

**The daily budget gate cannot fire. It is not a stale threshold — it is structurally measuring
nothing, and it will keep passing no matter what gets spent.**

Four independent agents surfaced this from different directions during the 2026-07-20 autonomous
arc (image generation, workflow-definition reconciliation, external-reach design, and the
orchestrator). Filing it once, properly, because `governance/` is human-edited only and this is a
decision, not a repair.

### The contradiction

- `governance/budget.yaml` sets `daily_usd_limit: 5.00`.
- `stack.md` budgets ~$15-30 per video, and the measured cost of `fyt-run-001`'s image stage alone
  is ~$17-18 (~130 Gemini calls at $0.134/img, 200-call working ceiling ~= $26.80).
- Both cannot hold. One video is 3-5x the daily cap.

### Why the gate passes anyway

`scripts/preamble.py` compares `budget.yaml` against **today's rows in `ledgers/cost/`**. Image
spend is never written there — every row today is a `0.0` subscription step. So the comparison is
`0.0 <= 5.00`, which passes trivially and would keep passing at any real spend level.

The gate is not protecting anything. It reads as a control and functions as a no-op.

### Why this matters more than the numbers

The failure mode is not "we overspend." It is **"we believe we have a spend control and we do
not."** That is the same shape as the severed `--allowedTools` cap found the same day: a mechanism
that presents as enforced, passes its own tests, and is disconnected from the thing it governs.
Both are worth fixing as a class, not individually.

### The decision is yours — three coherent options

1. **Make the ledger real.** Every API-billed step writes actual cost to `ledgers/cost/`, and
   `daily_usd_limit` is raised to a figure that admits one video (e.g. $35). The gate then means
   what it says. Most work; only option that yields a live control.
2. **Scope the limit honestly.** Keep $5.00 as a *subscription-step* limit, and govern API spend
   through per-run card authorisation instead (which is what actually happened for `fyt-run-001` —
   card `6a5d53ea-562cad3a` carried your verbatim authorisation). Requires renaming the key so it
   cannot be read as covering API spend.
3. **State that it is advisory.** Cheapest, and the only option that is *worse than doing nothing*,
   because a documented-inert control still reads as a control to the next agent at 3am.

Recommendation: **(2) now, (1) when the cost ledger is wired.** (2) is a rename plus a doc line and
makes the current true state legible immediately; (1) is the durable answer but needs the ledger
write path that does not yet exist.

### Also worth your ruling while you are here

`stack.md`'s Gemini spend-log row still records image generation as billing-blocked (HTTP 429) from
2026-07-03. **That is stale — the key generates.** ~130 calls succeeded on 2026-07-20. Anyone
reading `stack.md` to answer "can we generate images?" currently gets the wrong answer.
