## Work order

[HIGH] `cancelRun` (dashboard/server/control/execution.ts:1033-1137) never touches
`document.iterationLoops`. After the #188 hotfix (B1 stop-poisons-doc, B2 reconciler allowlist)
a rework-queued iteration loop whose producer attempt was stopped mid-flight loads correctly, but
no store API exists to advance or terminalize it — cancelling the parent run leaves the loop
stuck. A subsequent re-entry into that loop throws `AutomaticExecutionError` at
execution.ts:1459, every time, forever (no store state moves it out of the throwing path).

This is finding 1 of the opus adversarial review of PR #188, surfaced during the 2026-09-15 v1
launch rehearsal while exercising prod's real document.

Fix: add a store method that cancellation calls to drive any non-terminal iteration loop to
`parked` or `failed` as part of `cancelRun`, and make the re-entry path in `runAttempt`/wherever
execution.ts:1459 lives check for that terminal state instead of throwing.

## Acceptance
- New store method exists and is called from `cancelRun`'s cancellation path for every
  non-terminal loop on the document.
- Reproduced against the rev482 prod fixture (see Evidence): a rework-queued loop with a
  stopped producer attempt, cancelled via the fixed `cancelRun`, ends in `parked` or `failed` —
  not stuck.
- Re-entering that same loop after cancellation does not throw `AutomaticExecutionError`.
- `py -3 -m pytest` / vitest suites touching `execution.ts` stay green.
