## Work order

\# Fix: claude worker attempts never finalize on Linux — endStdin on terminal result event

\## Context (cold start)

Worktree `C:/Users/danie/kb-worktrees/boss-cloud-migration`, branch `claude/cloud-migration`
(verify with `git branch --show-current`). File: `dashboard/server/control/claudeWorkerAdapter.ts`.

The adapter spawns `claude -p --output-format stream-json --input-format stream-json --verbose`,
writes user frames to stdin, and deliberately NEVER ends stdin ("Stream-json accepts additional
user frames while a turn is live. EOF would close that channel." ~line 836). Normal completion is
detected ONLY via `proc.onExit` → `finalize`. VM-proven behavior (claude CLI 2.1.224, Linux): in
`--input-format stream-json` mode the CLI emits its terminal `result` event and then WAITS FOR
MORE STDIN — it never exits while stdin is open. So every governed attempt hangs until the
adapter timeout, even though the worker finished its work. (Probe evidence: with stdin ended,
the CLI exits ~200ms after the result event; with stdin open it is still alive at 90s.)
Older desktop CLIs exited after the result despite open stdin, which is why Wave-A passed on
Windows — the adapter was relying on CLI-version-specific behavior.

\## The fix (surgical — no redesign)

In the `proc.onStdout` handler (~line 808), complete lines are already framed in the
`while (newline !== -1)` loop that `tap`s each line. There, parse each COMPLETE line
(try/catch JSON.parse, malformed lines ignored — same tolerance as `parseWorkerStream`), and
when a parsed object has `type === 'result'`, call `proc.endStdin()` exactly once (guard with a
local boolean; `endStdin` on an already-ended stream must not throw — the default spawner's
`child.stdin?.end()` is already safe). Everything downstream stays as-is: the child now gets
EOF, exits, `onExit` fires, `finalize` parses the full captured stream exactly as today.

Semantics are safe because the `result` event ends the attempt's turn by contract: the engine's
states (succeeded / failed / waiting-human per lines ~524-526) are all derived from that result
event at finalize; `postMessage` live frames are only meaningful BEFORE the result; multi-turn
continuation uses resolveSession/recordSession (a NEW spawn resuming the session), not this
child. On Windows/older CLIs the child exited at result anyway — ending stdin then is a no-op.
Update the ~line-836 comment to state the new contract: frames may be posted until the terminal
result event; on result the adapter sends EOF so the CLI exits (newer CLIs wait for EOF).
