\## MEDIUM

- Crash recovery can repeat a side effect. The runner writes a card, invokes the desktop stage, and checkpoints completion only afterward ([runner.py:233-240, 316-358]). A crash after the remote operation but before `_save` causes the deterministic card path to be overwritten and the stage invoked again on rerun. `write_card` explicitly replaces an existing target ([jobs.py:242-250]). There is no issued-state/reconciliation step or execution idempotency key passed to the real CLI.

- SSH lacks a pinned-host policy and its remote no-network control is ineffective. The host is caller-provided and passed to `ssh`/`scp` without `StrictHostKeyChecking`, a dedicated known-hosts file, or an allow-list ([bridge.py:107-128, 252-260]). `KB_PROSPECTING_NO_NETWORK=1` is set only in the VM process environment ([bridge.py:180-184, 262-269]); it is not exported in the remote PowerShell command, so it does not constrain desktop CLIs.

- Bridge lifetime/cleanup is incomplete. Staging `ssh`/`scp` calls have no timeout ([bridge.py:104-132]), so the advertised 120-second timeout begins only after staging. A timeout before the first PID line is parsed cannot issue remote `taskkill` ([bridge.py:273-288]). Remote cleanup is best-effort and unverified ([bridge.py:319-321]); the VM-side `job.json` is never removed. Every invocation also uses the same local and remote name ([bridge.py:99-106, 225-229]), so concurrent runs can stage or execute each other’s job.
