\## Task decomposition required (order; split if >8 steps)
1. Evidence store ops (`personalizer/evidence.py`): insert/list/expire evidence rows bound to
   person+campaign; `allowed_for_copy` enforcement; confidence floor from policy; source must be a
   `source_snapshot` id or a URL present in a snapshot (no free-floating claims); tests incl. expiry
   and floor.
2. Template registry (`personalizer/templates.py` + `orgs/prospecting/templates/*.txt`): port the
   four non-sales families from r2 §3 as skeletons with named slots `{first_name}`, `{company}`,
   `{why_them}`, `{ask}`, `{sender_proof}` etc.; `template_id`+`template_version`; slot inventory
   per template; a validator that rejects unknown slots; tests per template.
3. Sender profile (`orgs/prospecting/sender-profile.yaml` schema + loader): name, school,
   background line, proof point(s), signature; PII of DANIEL only (allowed); validated; tests.
4. Slot binding + QA (`personalizer/qa.py`): every filled slot maps to an evidence id or a
   sender-profile field or a policy field; word count 60-120; exactly one ask sentence; ask type
   matches policy; no referral ask on step 1; no link/URL/attachment mention; no sensitive-inference
   terms (list from spec threat model); name-swap check (body must not remain valid if first_name
   and company are swapped with another person's — implement as: at least one evidence-backed slot
   is person-specific); returns structured QA result; tests for each rule red/green.
5. Revision builder (`personalizer/revision.py`): assemble subject+body from template+slots, compute
   `revision_hash` (sha256 over canonical JSON of subject, body, recipient contact_point_id, mailbox,
   template_id+version, evidence_ids, prompt+model version), insert `revision` row with QA result;
   idempotent on identical inputs; tests.
6. Model I/O contract (`personalizer/model_io.py`): the JSON the skill's model turn must return
   (`angle`, `why_them` text, `ask` text, `evidence_ids_used`, `self_critique`), strict schema
   validation, rejection of any field containing a URL/email/phone, injection guard (snapshot text
   is inert: any instruction-like content in evidence excerpts is stripped/flagged), tests with fake
   responses (good, missing evidence id, hallucinated id, over-length, link).
7. Job runner CLI (`personalizer/cli.py`): `personalize --list <id> --policy <id> --model-response
   <json>|--fake`: for each person: load evidence → choose template by intent → call model contract
   → bind → QA → revision; summary JSON counts only (PII guard on output); resumable; tests via
   fake model over the P1 synthetic fixture list.
8. Slim skill `skills/curated/prospecting-personalizer/SKILL.md` + `prompt-contract.md`: behavior-
   changing text only (inputs, the exact CLI calls in order, the JSON it must emit, hard rules,
   stop conditions); ≤120 lines; a test that the skill's referenced CLI commands exist and that it
   contains no prose paragraph longer than 3 lines (lint).
9. Inspector suite draft: `evals/` is human-blessed (rule 8) → write the draft eval cards to
   `orgs/prospecting/evals-draft/personalizer/*.md` (5-8 falsifiable checks from spec §Agent
   contracts), each runnable as a pytest against fake-model fixtures.
10. Gate: `gate_manifest.json` P3 entries, `gate.py --phase P3` numeric criteria from spec §P3;
    20-draft synthetic run with the fake model; final task runs the gate.
