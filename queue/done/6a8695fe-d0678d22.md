\## Findings (address all 27)

1. CRITICAL — Cards are projected from the bare mirror but ACTED on via the
   agent-writable checkout (driveVerify(cardPath,{repoRoot}) with repoRoot =
   /var/lib/kb/ops inside ReadWritePaths): Daniel approves one body, a different one
   can execute. Fix: every card InboxItem carries the projected blob SHA; the
   response/verify endpoint requires it and refuses unless the executed copy hashes
   identically (or executes directly from the pinned mirror object).
2. HIGH — Bare mirror at /var/lib/kb/state/inbox-ops.git sits inside the dashboard's
   ReadWritePaths=/var/lib/kb/state, voiding the isolation claim. Fix: mirror lives
   under the kb-github-integration uid outside dashboard ReadWritePaths (e.g.
   /var/lib/kb-github/inbox-ops.git), dashboard-readable only.
3. HIGH — Attempt-finally park doesn't stop the engine's batch loop (runToBoundary
   proceeds to prepareOrContain + next Promise.all; transitionRun then throws on the
   parked run, execution.ts:943,948-951,2481-2486); the batch loop is absent from the
   FenceParticipant list. Fix: batch loop = named fence participant; check the
   persisted fence before prepareOrContain and before each batch; return a `parked`
   boundary outcome so the loop exits cleanly.
4. HIGH — Detached post-response promise chains (routes.ts:1936 `void
   execution.then`, :1988 `void execution.catch`) can mutate/un-park a parked run
   after the fence. Fix: route both through the same store CAS predicate as the park
   (no-op when lifecycle is paused-for-deploy with matching deployment ref); §7 test
   "fence while a detached execution handler is pending".
5. HIGH — Crash during rehydration leaves a stale resumeClaim that the
   different-bootId rule converts into a permanent intervention. Fix: under the OS
   lock a claim with a NON-current bootId is stale by construction — reclaim and log;
   duplicate-writer fault only for a current-bootId claim from an unexpected source.
   State pendingActivation-vs-resumeClaim precedence in normalizeCrash (today
   :3276-3277 sends pending-activation recovering rows to waiting-human).
6. HIGH — Fence enumerated at callers though a complete chokepoint exists one layer
   down: every spawn goes through dispatchClaimedCard (queueBridge.ts:578) or
   ManagedSessionAdapter.start (claudeSessionAdapter.ts:143). Fix: mandatory fence
   check INSIDE those two; participant registry kept for drain acknowledgement only;
   lint/meta-test that no module outside them reaches the spawner.
7. HIGH — T3 approvals execute cards on verify (approvals/inbox.ts:171-173) and are
   not a fence participant; a passkey approval during a fence launches work post-park.
   Fix: add approvals-verify/execute to the registry; 409 deploy-pause-active before
   deps.execute; assertion stays valid for replay after resume.
8. HIGH — One live persistent PTY session blocks deploys indefinitely (liveCount over
   sessions designed to outlive browsers), refusal not actionable, and KillMode kills
   PTYs at swap anyway. Fix: per-session last-activity; refuse only on sessions active
   within N minutes; refusal returns blocking sessionIds as an Inbox item with a
   one-click "close and deploy" action.
9. HIGH — 35-min deadline turns a long attempt into a long wait that then FAILS —
   worse than the old gate; FYT render attempts routinely exceed it. Fix: deadline
   expiry is non-terminal — deployment stays `requested`, fence held, parks at the
   next attempt boundary whenever it arrives; surface live progress ("waiting on
   attempt X, running Nm") + explicit human Abort. Hard expiry only for the swap
   window (swapping→resuming).
10. HIGH — Inbox "Pull home" has no executor (endpoint on VM, mechanism desktop-only,
    v2 helper closed to deploy fields, phases 6/7 ordering). Fix: VM POST records
    intent; the desktop helper gains a second closed `pull-assets` verb bound to
    runRef + manifest digest — or declare the item a notification with external/
    deep-link semantics. Pick one and specify it.
11. HIGH — Post-finalization boot-recovery failures have no resident alerting owner
    (activator gone, recovery timer cancelled; wake_me is a library call). Fix:
    resident systemd timer polls /readyz unconditionally; fires deduplicated wake-me
    on startup-recovery-failed or bridge stopped past a threshold, independent of any
    deployment.
12. HIGH — Deliberate rollback lacks journal phases; SIGKILL after `down` but before
    swap → next boot auto-up-migrates and the rollback silently vanishes. Fix: journal
    + recovery-table rows for rollback (rollback-authorized, rollback-stopped,
    down-migrated, rollback-swapped); loader refuses to auto-up a store whose journal
    records an in-flight rollback.
13. HIGH — Bootstrap step 0 underspecified: today's wait_healthy returns on ok:true
    and raises at 60s (activate_release.py:277-288); the FIRST pause-engine release
    returns ok:false+deployment-rehydrating >60s → auto swap-back. Fix: step 0's
    compatibility activator explicitly includes retryable/fatal blocker discrimination
    + the parameterized 15-min wait; step-0 acceptance test for exactly this case.
14. HIGH — If kb-deploy.socket is an activating socket unit, a stray connect restarts
    the dashboard mid-swap (between stop and start). Fix: non-activating socket (or
    activator stops kb-deploy.socket first in step 2, restarts after step 5). State it.
15. HIGH — Lock fd needs O_CLOEXEC (Node fs.open doesn't set it; an escaped child
    holds flock forever → permanently unstartable dashboard, activator hangs). Fix:
    open with O_CLOEXEC + test asserting it; activator stop-confirmation falls back to
    cgroup-empty, readiness blocker reports the holding PID.
16. MEDIUM — Single-writer lock breaks synthetic-acceptance's second store
    construction (makeSurfaceContext builds the store unconditionally,
    surface.ts:138; two flocks conflict even in-process). Fix: acquire the lock once
    at the process entrypoint; createFileControlPlaneStore gets an explicit
    already-locked/read-only harness mode; say which mode synthetic acceptance uses.
17. MEDIUM — Legacy migrations live INSIDE normalizeCrash (prepareLegacyStoreMigration

18. MEDIUM — Per-mutation double-fsync on a synchronous full-document rewrite blocks

    park/ack into single transactions; double-fsync only deploy-critical mutations;

19. MEDIUM — Activator writes the store during snapshot restore without the

20. MEDIUM — Automatic swap-back on VM-reported readiness = downgrade primitive for a
