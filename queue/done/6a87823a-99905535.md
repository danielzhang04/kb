\## Why
kb's dashboard (`dashboard/`, React + Node daemon, runs on a desktop and on a Linux VM) is being
rebuilt. The operator's complaints, verbatim themes: too many isolated boxes; too much technical
text and raw IDs; can't click into a running agent and watch it; loops/schedules/runs/agents are
five separate surfaces; inbox overpopulated and never clears; terminals tiny; graph for "all agents"
that aren't connected; naming/casing ugly. The agreed direction (binding rules, do not argue them):

1. Two runnable nouns — Agent and Workflow; a "loop" is a schedule on either. Runs live INSIDE the
   entity that owns them.
2. Card above the fold = human name, status pill, model, last/next run, host. Nothing else.
3. Click-in = the live CLI stream (like reattaching to a running `claude`/`codex` terminal) with a
   need-to-know sidebar (plan, milestones, built links, outputs).
4. No raw identifiers in prose; technical payload behind one "Details" disclosure.
5. Detail slides in over the list; list keeps its place.
6. Box grid for entities, rows for logs.
7. Build where the thing lives ("New agent" on Agents), no global "+ New".
8. Nothing stays healthy by hand-triggering; schedules armed by default, UI shows next fire.
9. Inbox = high-level only (deploys, PRs, learnings, escalations); run-level human gates are
   notifications on the entity + inside the run, resolve in place, auto-clear.
10. Test/lint output is evidence inside a run, never a panel.
11. Visual: dark neutral (Claude-desktop warm near-black family), SHARPER contrast steps, one
    tasteful accent for selection/focus only, semantic colors only for state, hairlines, condensed.
12. Sidebar grouped by altitude: Operate / Build / Learn / System.
13. Full-screen browser terminal (real shell: claude, codex, filesystem).
