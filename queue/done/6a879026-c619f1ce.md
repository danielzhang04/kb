\### D3. Card anatomy (both nouns)
Above the fold, exactly: human name (Title Case, derived from id: `fyt-checker` → "FYT Checker";

\### D4. Entity page = slide-in over the list (list keeps scroll/filter)
Tabs: **Live** (default) — active runs as rows: state, elapsed, tools called, last line; click → the
run view. Empty state says when it last ran and when it runs next. **Brief** — the one-minute read:
one sentence of what it is for; what it is doing now; last 5 runs as one-liners (time · outcome ·
one-line result); outputs it produced recently with links (files/artifacts/PRs); pending gates;
its schedule; its autonomy tier in one sentence. **Details** — a single disclosure BUTTON, closed by
default, containing everything technical today's AgentDetail/Agent Management/Autonomy Ladder/
Run Envelope show (source path + revision, tools, declared ceiling, what it replaces, builds on,
knowledge sources, skills, schemas, lineage, grades, ids). Actions (secondary, top-right): Run now ·
Schedule (opens New-schedule prefilled) · Edit · Open terminal (attach a shell in its cwd).
Workflows additionally show a graph of THIS workflow's steps with live state (from the run DAG);
clicking a step opens that step's stream. No fleet-wide graph anywhere.

\### D5. Run view = the stream
Full-width live stream of the session, as if reattaching to the CLI: for claude/codex runs the
transcript stream (today's Timeline/SSE model; keep live↔replay parity); for PTY sessions the
terminal itself. Right inspector (collapsible): plan, milestones, built links/outputs, and — when
the run waits on a human — the gate prompt with its respond/approve controls, resolved HERE. One
Details disclosure (closed) for step skeleton / envelope / cards / ids. Test, lint and self-check
output is evidence inside this stream/Details, never a surface of its own.

\### D6. Gate counts (replaces Inbox for run-level gates)
A run awaiting a human contributes 1 to: the Agents or Workflows sidebar entry badge, its entity
card badge, its Live tab badge. Resolving in the run view decrements all three (derive from one
store query; never three counters). Run gates never appear in Inbox.

\### D7. Schedules page (like Claude's scheduled tasks)
Lists ONLY existing schedules: owner (agent/workflow), cadence in words, next time (EST, no timezone
UI anywhere), last outcome, armed toggle, delete. "New schedule" = pick an existing agent or
workflow → cadence (words or cron) → time → create. Never lists unscheduled entities, never shows
"proposed" schedules. System agents ship with SEEDED, ARMED default schedules (visible here, editable).
Next time also renders on the owner's card. Reuse `dashboard/src/lib/scheduleWords.ts` and the
existing schedules/HEARTBEAT substrate — say exactly which code stays and which goes.

\### D8. Learnings pipeline (no page)
Miners (lessons miner, grader, model audit, hygiene, context lifecycle) are System agents on
schedules; their proposals are written to the filesystem under a path you choose in the repo's
existing conventions (say where and the record shape). A **Learnings Implementer** System agent runs
on a schedule, batches unimplemented proposals, makes the changes on a branch, opens a PR through
the existing durable PR path (`runtimeCapabilities.durablePrWrites`; workers never commit to
main; the VM never merges). That PR is an Inbox item (D10). Merged = implemented; the record is
marked and stays on disk for agents; the dashboard never shows learning history. The five panels
that showed this data are deleted; the data remains reachable as those agents' runs (Brief/Details).

\### D9. Deploy (absorbs vm-movement §3)

Deploys page. State machine is the movement spec's; reference, don't restate.

\### D10. Inbox (high level only)
Items: PRs / merge requests awaiting Daniel (including Implementer PRs), Deploy ready / deploy

System sweeper reconciles the rest. No read/snooze/resolve controls, no retention cap, no archive.
Actions per item: Open PR (external, labelled), Deploy / Acknowledge, Open card. Empty state says
"nothing needs you" plus the next scheduled fire.

\### D14. Placement (agents run where their tools live) and `/api/v1`
The builder (New agent / New workflow, on their own pages; form-first, no chat) assigns tools and

capabilities (connectors present, PTY, GPU, logged-in CLIs). The scheduler routes a run to a host

it over `/api/v1`, so a Gmail/browser agent built on the VM runs on the desktop unattended and is
watched from either dashboard. No "needs" field, no extra ceremony in the builder. `/api/v1` =
versioned JSON envelopes for agents, workflows, runs, schedules, inbox, actions, health, under
tailnet auth (movement spec §6) — the seam Atlas (a separate desktop app) will use. Design the
minimum that serves placement + Atlas; list the endpoints.
