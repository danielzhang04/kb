## Work order

\# Build: tailnet-mode client auth (dashboard UI stuck on a dead passkey sign-in)

\## The bug (verified by the boss)
The VM dashboard runs in **tailnet auth mode** (`DASHBOARD_AUTH_MODE=tailnet`). Server-side auth is
CORRECT and must not change: `dashboard/server/http/middleware.ts#resolveSession` authenticates every
request via the ambient tailnet identity (`operatorAuth.authenticate`, `auth/tailnetOperator.ts`) and
mints a real session with **no client bearer needed**.

But the **client** was never taught tailnet mode. `dashboard/src/lib/sessionContext.tsx` computes
`locked = !isSessionFresh(session)`, and `session` only ever comes from a WebAuthn-minted bearer
(`authClient.signIn` → `POST /api/auth/assert/options`). In tailnet mode there is no bearer, so
`locked` is always true → `App` renders `SignInView` → it calls `/api/auth/assert/options`, which
CORRECTLY returns 503 (`DASHBOARD_RP_ORIGIN` is deliberately unset in tailnet mode). Result: the human
UI is stuck forever on a passkey ceremony that physically cannot complete, even though the API and the
armed platform work fine.

\## Goal
In tailnet mode the client must render the app **unlocked, with no sign-in ceremony** (the transport
already authenticates every fetch). In `win32-desktop` mode, behavior stays **bit-for-bit unchanged**
(the passkey flow). One clean mode switch, fail-closed.
