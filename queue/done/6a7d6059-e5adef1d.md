\## The defect (MAJOR, from the delta re-review, verbatim)

`hasBlockingIterationRequest` (`store.ts:2532-2539`, wired at 5010/5226/5774) blocks on every
open `approval`/`intervention` whose `gateKind !== 'iteration-park'` — but an iteration
COMPLETION gate carries no `gateKind` (`store.ts:5070`), so it reads as a foreign run gate.
Probe: with sibling group LEFT holding an open post-acceptance completion gate, RIGHT group's
turn request refused `ineligible: iteration turn is blocked by an open gate or intervention`.
Violates the proposal ("Other groups in the run may continue to advance and settle against
their own state") and the ruling "iteration-owned gates stay group-scoped".

\## The fix (reviewer-specified)

Scope by IDENTITY, not by gateKind: a request is iteration-owned when some iteration receipt
claims it via `completionRequestRef` or `interventionRequestRef` (the existing
`isReviewLinkedRequest` at `store.ts:1340` covers this). Blocking rule for a loop's
rework/turn launch:
1. this loop's OWN two refs (its completion gate / park gate) block it, AND
2. any open approval/intervention that NO iteration receipt claims (foreign run gates —
   launch reconciliation, manager shutdown, etc.) blocks it;
3. gates claimed by OTHER loops' receipts do NOT block it (group scoping).

Add the sibling-completion-gate regression test alongside the existing park-gate one:
LEFT group awaiting-completion-gate open → RIGHT group's turn request proceeds.
