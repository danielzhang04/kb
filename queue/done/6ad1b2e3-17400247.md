## Result

Verdict: **B — the administrator-only fresh parent-SACL gate is technically unnecessary for this same-volume, identity-preserving rename.** It is an overbroad carryover from the replacement-recovery contract, not a requirement of `MoveFileExW(..., 0)`.

Why:

- The adapter performs a no-replace, no-copy rename of the existing directory object and verifies the same native root identity afterward ([adapter](/C:/Users/danie/Projects/Filesystem-Cleanup/scripts/ait25-cutover-live-r2.ps1:373), [Apply](/C:/Users/danie/Projects/Filesystem-Cleanup/scripts/ait25-cutover-live-r2.ps1:718)).
- Microsoft states that a default security descriptor is assigned only when an object is created, “not when it is renamed or moved.” A security descriptor includes owner, group, DACL, SACL, and control bits. Therefore, for the checked same-volume rename, the existing object’s SACL is not recalculated from either parent. This is an inference from Microsoft’s documented rename and security-descriptor rules. [File security and access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [security descriptors](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors).
- `MOVEFILE_COPY_ALLOWED` is absent. Microsoft documents that cross-volume behavior requires that flag for files, while directories must stay on the same drive; cross-volume copying is the case where the original security descriptor is not carried over. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
- The scanner and comparisons read owner/group/DACL only, and the adapter exposes no ACL or SACL setter ([fields](/C:/Users/danie/Projects/Filesystem-Cleanup/scripts/ait25-cutover-live-r2.ps1:164), [parent baseline](/C:/Users/danie/Projects/Filesystem-Cleanup/scripts/ait25-cutover-live-r2.ps1:583)).
- The elevated audit reads the two parents, not the source tree’s unknown SACL. It therefore cannot make the retained recovery capable of restoring the source SACL. It also explicitly omits mandatory-label information ([parent reader](/C:/Users/danie/Projects/Filesystem-Cleanup/scripts/read-ai-parent-security.ps1:178)).
- Previously empty parent audits are historical evidence only. They must not be called current or used to relabel today’s unread parent SACL as empty.

The important distinction is:

- **Same-object rollback:** reverse `MoveFileExW(destination, source, 0)` after exact identity and tree verification. The same object—and therefore its existing unknown SACL—moves back. No SACL reconstruction occurs.
- **Replacement recovery:** if the original object is lost and recovery creates replacement objects, the accepted backup cannot restore or verify the source SACL. That limitation remains unchanged before and after the rename.

Smallest ordinary-user protocol:

1. Omit `-ParentAudit`.
2. During `Prepare`, retain the existing checks for ordinary, non-reparse parents; native identities; source-parent equality to captured provenance; current owner/group/DACL bytes; same volume; destination absence; exact source/recovery reconciliation.
3. Bind both parent identities and owner/group/DACL bytes into the checkpoint.
4. During `Apply`, re-read and require those parent values to be unchanged, recheck the source tree, destination absence, window, approval, and writer pause, then perform exactly one flags-0 rename.
5. Verify the destination has the same root identity and exact tree snapshot. Retain all backups.
6. Permit automatic rollback only while the destination still matches the accepted post-rename snapshot and the old path remains absent.
7. Keep these statements explicit: `source SACL UNKNOWN`, `parent SACL current state UNKNOWN`, and `replacement recovery cannot reproduce source SACL`.
