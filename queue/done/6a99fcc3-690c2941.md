\## Architecture

The VM may assemble IDs and display a PII-free summary, but it never receives names, addresses,
message bytes, credentials, or a send capability. The canonical approval scope is staged as the
work-order bytes of a normal kb approval card. The dashboard signs those committed bytes; the
desktop verifier imports the existing kb WebAuthn verifier, acts only on the verifier's pinned
card/result, and never parses public-key material itself.

A batch scope binds the campaign, policy, sorted exact revision/contact pairs, batch hash, mailbox,
T1 tier, permitted window, expiry, and a random parent nonce. Materialization is one transaction.
The first approval uses the parent nonce and later rows use deterministic child nonces derived from
the parent nonce plus the exact item. This preserves the P1 unique approval.nonce contract, makes
replaying the assertion fail the entire transaction, and leaves each send with a separately
consumable nonce. Each row's scope_hash is the canonical hash of its exact send scope.

The T1 executor is the only live-send path. It scans inbound first, refreshes the Gmail thread,
rechecks every bound field and all hooks, compare-and-set claims the delivery, and consumes the
matching approval in the same SQLite transaction immediately before the Gmail adapter call.
Follow-ups continue through P4's draft path. T2, T3, sales, and reply-template automation remain
fail-closed.
