Defect: `WorkManager.cancel(job_id)` (1) can race a still-QUEUED/LAUNCHING launch thread — the thread
later transitions the job to RUNNING, resurrecting a cancelled job and leaving a live Claude session
nobody tracks; (2) transitions already-terminal jobs (SUCCEEDED/FAILED/CANCELLED) to CANCELLED and fires
the terminal callback a second time.

Required behaviour:
- `cancel` on a terminal job is a no-op that returns the job unchanged and fires no callback.
- `cancel` on QUEUED/LAUNCHING marks the job CANCELLED immediately; the launch thread, after `launch`
  returns, observes that state under a per-job lock and calls `launcher.cancel(session_id)` instead of
  transitioning to RUNNING (it already checks this — make the check and the RUNNING transition atomic
  with `cancel` via one `threading.Lock` so the race cannot interleave).
- `cancel` on RUNNING calls `launcher.cancel`, then CANCELLED, callback once.
- The terminal callback fires exactly once per job across every path (keep `_notified`).

open): cancel-while-launching never becomes RUNNING and cancels the session; cancel on each terminal
state is a no-op with no callback; cancel on RUNNING; callback-once across cancel+poll.
